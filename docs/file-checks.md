# 文件级机检与写文件协议（v0.7.15）

## 这层为什么存在

v0.7.14 为止，MAS 的**全部**机检都只搜**模型输出的文本**。这能证明
「答案里包含这一段」，但永远无法证明「磁盘上那个文件现在是这样」。

于是最要命的那类假闭环成立了：

> worker 说「已把结论写入 `out/report.md`」，产出一段很像样的说明；
> 引擎搜文本，没搜到期望的字符串 → 不通过 → 重试 → 再说一句 → 再不通过 → 烧完预算。
> 而如果期望字符串碰巧也出现在那段说明里，引擎甚至会**判定通过**，尽管磁盘上根本没有那个文件。

闭环建立在**承诺**上，不是**事实**上。v0.7.15 加的两样东西就是来拆掉这个前提的：

| | 方向 | 作用 |
| --- | --- | --- |
| **文件级机检** | 读侧 | 判定只认真实文件系统上的字节 |
| **写文件协议** | 写侧 | 给 worker 一个**真的**把文件写到磁盘上的途径 |

两边必须配套：有读侧没写侧 → 检查永远过不了；只有写侧没读侧 → 写了也证明不了。

## 文件级机检

### 十种检查

| type | 含义 | 参数 |
| --- | --- | --- |
| `file_exists` | 文件存在且是普通文件 | `path` |
| `file_missing` | 文件不存在（清理类验收） | `path` |
| `file_contains` | 文件含给定字符串 | `path` + `value` |
| `file_not_contains` | 文件不含给定字符串 | `path` + `value` |
| `file_regex` | 文件内容命中正则 | `path` + `value` |
| `file_lines_min` | 非空行数下限 | `path` + `value`（整数） |
| `file_min_bytes` | 字节数下限 | `path` + `value`（整数） |
| `file_max_bytes` | 字节数上限 | `path` + `value`（整数） |
| `file_sha256` | 文件 sha256 等于给定摘要 | `path` + `value` |
| `file_mtime_newer` | 文件修改时间晚于给定 ISO 时间戳 | `path` + `value` |

### 参数写法

推荐对象形式：

```json
{
  "id": "report-written",
  "desc": "报告已落盘且含结论",
  "check": {
    "type": "file_contains",
    "arg": {"path": "out/report.md", "value": "结论"}
  }
}
```

也支持 CLI 简写字符串形式 `"path::value"`：

```bash
mas run --goal "..." \
  --criteria 'file_exists:out/report.md' \
  --criteria 'file_contains:out/report.md::结论'
```

### 判定口径（与文本机检一致的纪律）

| 情况 | 结果 | 理由 |
| --- | --- | --- |
| 文件存在且满足条件 | `pass: true` | — |
| **文件缺失**（对 `file_exists` / `file_contains` 等） | `pass: false` | 缺失是**失败**，不是「无法判定」 |
| 路径越界（`../` 或工作区外的绝对路径） | **开跑前拒绝** | 标准不该能读用户整块硬盘 |
| 路径合法但无法判定（如目录、二进制解码失败） | `pass: null`（unjudged） | 读不懂就是读不懂，不猜 |
| 参数缺失 / 类型不认识 | **开跑前拒绝** | 写漏了 = 标准作废，不是标准通过 |

报告里文件级判定的 `source` 是 `"file"`，与文本机检的 `"rule"` 区分开——
复盘时能一眼看出这条结论是**从磁盘来的**还是**从文本来的**。

### 工作区（workspace）

文件路径一律相对**工作区**解析，而不是相对当前工作目录：

```bash
mas run --workspace ./my-project --goal "..."
```

这样从任何目录启动，跑的还是同一个文件。默认工作区 = 当前目录。

安全边界：

- 路径不能逃出工作区（`../../etc/passwd` 一律拒绝）；
- 工作区外的绝对路径也拒绝，除非它本来就在工作区里；
- 单文件读取上限 8 MiB，超出即拒绝判定。

## 写文件协议

### 为什么需要它

加了文件级机检之后，第一轮真实端点实测立刻暴露了缺口：
**worker 根本没有写文件的途径**——它的输出只是一个字符串。于是它只能「说」自己写了，
检查理所当然地失败，循环永远闭合不了。

协议给 worker 一个明确、有限、可审计的表达方式：在交付文本里嵌入围栏块。

### 块格式

```
<<<MAS:FILE path="notes/finding.txt">>>
这里是文件内容，逐字写入。
<<<MAS:END FILE>>>
```

引擎会：

1. 解析出路径与内容；
2. 把块**从产物里剥掉**（产物仍然是可读的交付说明）；
3. 在工作区内创建父目录并**原样写入**（不做任何模板替换）；
4. 在账本里记一笔 `role="write"`，谁在什么时候写了哪个文件都能查。

### 安全规则

- 越出工作区的路径**拒绝写入**，并报 `refusing to write outside the workspace`；
- 单文件上限 4 MiB，超限拒绝；
- 路径为占位符（如 `相对路径`）时**跳过**——指令里的模板块被模型照抄时，
  不该真的生成一个叫「相对路径」的文件，更不该让占位内容骗过 `file_exists`；
- 块未闭合、路径为空 → **保留原文在产物里**并报错误，绝不吞掉半个请求。

### 写法上的两个细节

- 闭合标记写 `>>>` 即可；`>>>>` 和历史版本的 `>{3,}` 写法也都能解析。
  （早期指令里误把正则量词 `>{3,}` 当字面量交给模型，导致模型照抄后解析失败——
  这是实测发现并修掉的 bug。）
- 内容里的 `<<<MAS:END FILE` 会被当作**第一个**闭合标记，所以文件内容本身
  不要以该标记开头。

### 并行候选：只写胜出的那一个

并行模式下有多个候选产物。引擎**只把胜出的候选**写到磁盘——
否则工作区里会同时留下好几个版本的同名文件，文件检查就会「谁最后写谁算数」，
检查也就不再描述真正交付的那份产物了。

## 一条完整的验收标准

```json
{
  "id": "finding-on-disk",
  "desc": "结论真的落到了 notes/finding.txt",
  "required": true,
  "check": {
    "type": "file_contains",
    "arg": {"path": "notes/finding.txt", "value": "MAS-FILECHECK-LIVE-TOKEN"}
  }
}
```

这条标准会：

1. 从标准里推导出「worker 必须写 `notes/finding.txt`」这一**文件义务**，
   写进 worker 的任务说明；
2. worker 用写文件协议交付 → 引擎落盘；
3. 引擎读磁盘 → 命中 → `pass: true`，`source: "file"`；
4. worker 只说不写 → 磁盘上没有 → `pass: false` → 循环**不闭合**。

`file_missing` 故意**不产生**文件义务——它断言的是文件已经不在了。

## 实测结论（v0.7.15）

在真实端点（`claude-opus-5-5` @ `127.0.0.1:16024/v1`）上跑同一份标准：

| 场景 | 结果 |
| --- | --- |
| worker 声称「已写入」但磁盘上没有文件 | `status=budget_exhausted`，`closed=False`，判定 `pass=false`，`note="file not found: out/report.md"` |
| worker 按协议真写了文件 | `status=closed`，`closed=True`，判定 `pass=true`，`source="file"` |

这就是这层存在的意义：**文件级机检跟的是磁盘，不是文案。**
