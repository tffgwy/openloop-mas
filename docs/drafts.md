# 草稿层：改动先进草稿，人确认后才写回原文件

从 v0.7.72 起，循环**不再直接覆盖你的文件**。

当一次运行想改一个**已经存在**的文件时，它会：

1. 把新内容**放进一份草稿**（`.mas-drafts/`），
2. **原文件一个字节都不动**，
3. 草稿带一份**可读的 diff** —— 你先看清改了什么，
4. 你说「批准」，改动才**写回原文件**；你说「驳回」，**一个字都不改**。

```bash
mas drafts                                   # 看有哪些草稿在等
mas drafts show D-1a2b3c4d                   # 看这一份的 diff
mas drafts approve D-1a2b3c4d                # 批准：写回原文件
mas drafts reject  D-1a2b3c4d                # 驳回：原样不动
```

四个动作都有 `--json`，给脚本和 agent 用。

---

## 为什么要有这一层

一个多智能体循环最危险的时刻，不是它跑不动，而是它**跑得太顺**：
worker 说「我把文件改好了」，引擎就真的把文件覆盖了，
**你原来写的东西没了，而你甚至没看见它被改成了什么。**

这条规则不是本项目发明的。MOKI（DeepSeek Harness 的本地资源管理器插件）
就是这条规则：**修改先进草稿，用户审核确认后再保存回原文件。**

MOKI 在**交互层**做这件事 —— 你选中一段文字，按 `Alt+D` 唤起 AI 对话，
改完先进草稿。本项目在**引擎层**做同一件事 ——
不管改动是模型提的、agent 提的、还是脚本提的，
只要它想覆盖一个已有的文件，它就**必须先变成草稿**。

---

## 草稿放在哪

草稿和它改的那个文件**住在同一个工作区里**，文件夹是 `.mas-drafts/`：

```
<state_dir>/artifacts/<run_id>/
├── deliverable.md          ← 交付物
├── notes.txt               ← 你的文件，原样不动
└── .mas-drafts/
    ├── D-1a2b3c4d.json     ← 草稿的元数据（含 diff）
    └── D-1a2b3c4d.data     ← 草稿的字节本身
```

**为什么不放在中心目录？** 一个住在中心目录的草稿，会在文件夹被复制的时候
一起丢失；而丢掉的草稿，是一份**永远没法被人审阅**的改动。

**为什么字节单独存？** diff 是**改动的报告**，不是**改动本身**。
批准的时候要写回的是 **worker 产出的那些字节**，所以字节也得存着。

---

## 草稿里有什么

每份草稿是一段 JSON：

| 字段 | 是什么 |
| --- | --- |
| `id` | 草稿编号（`D-` 开头） |
| `path` | 相对工作区的路径 |
| `state` | `pending` / `approved` / `rejected` |
| `reason` | 为什么提出这个改动 |
| `before_sha256` / `after_sha256` | 改动前后的哈希 |
| `before_bytes` / `after_bytes` | 改动前后的字节数 |
| `changed` | 是不是真的改动了（内容一样就是 `false`） |
| `diff` | 可读的 unified diff |

---

## 什么**不**走草稿

**新建文件照常直接写。** 一个还不存在的文件，
没有任何东西可以毁掉 —— 草稿规则是为了**不毁掉已有的工作**，
没有工作可毁的时候，规则就不该添乱。

所以 `mas drafts` 里出现的，永远是**对已有文件的改动**。

想回到旧行为，把配置里的 `edit_policy` 改成 `"overwrite"`：

```json
{ "edit_policy": "overwrite" }
```

**默认是 `"draft"`。**

---

## 机检看的是草稿里的字节

这是这一层最容易做错的地方。

**如果机检读的是磁盘上的旧文件**，那循环就会陷入死结：
它提一个改动 → 机检读旧文件 → 机检判不通过 → 循环改 → 再提一个改动 →
还是读旧文件……**永远闭不上**。

所以机检读的是**草稿里的新字节** —— 一个只存在于内存里的 overlay，
**不碰磁盘**。这样循环可以**用自己的提案闭合**：

> 批准与否，是关于**那个文件**的，不是关于**这次判定**的。
> 循环该跑完就跑完，文件该不该被改，由人说了算。

这和并行候选排序用的 overlay 是同一个想法。

---

## 边界

- **草稿只对工作区里的文件成立。** 工作区外的路径照旧被拒绝。
- **一份草稿只能批一次。** 批过之后再批会被拒。
- **驳回不会删草稿**，它只是把状态标成 `rejected` —— 人能看见
  「这份改动被看过、被否了」。
- **门禁 `draft_approval`** 盯着这一层：覆盖变成草稿、原文件字节不变、
  新建文件照常直接写、草稿带 diff、机检看到草稿字节、批准才写回、
  驳回一个字都不改 —— **八条变异全部被捕获**。

## 和 MOKI 的关系

| | MOKI | 本项目 |
| --- | --- | --- |
| 位置 | **交互层**（DeepSeek Harness 的插件） | **引擎层**（闭环运行时） |
| 触发 | 选中文字 → `Alt+D` | 任何一次运行或 agent 提的改动 |
| 预览 | 交互式预览 | `mas drafts show` 的 diff |
| 批准 | 交互式确认 | `mas drafts approve` / MCP 工具 |

两者是**互补**的：MOKI 管**你手边的文件**，本项目管**循环跑出来的东西**。
规则是同一条。
