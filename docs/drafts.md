# 草稿层：改动先进草稿，人确认后才写回原文件

从 v0.7.72 起，循环**不再直接覆盖你的文件**。

当一次运行想改一个**已经存在**的文件时，它会：

1. 把新内容**放进一份草稿**（`.mas-drafts/`），
2. **原文件一个字节都不动**，
3. 草稿带一份**可读的 diff** —— 你先看清改了什么，
4. 你说「批准」，改动才**写回原文件**；你说「驳回」，**一个字都不改**。

```bash
mas drafts                                   # 看有哪些草稿在等
mas drafts show D-1a2b3c4d                   # 看这一份的 diff
mas drafts approve D-1a2b3c4d                # 批准：写回原文件
mas drafts reject  D-1a2b3c4d                # 驳回：原样不动
mas drafts token                             # 拿人类令牌（agent 批不了自己的草稿）
```

四个动作都有 `--json`，给脚本和 agent 用。

---

## 为什么要有这一层

一个多智能体循环最危险的时刻，不是它跑不动，而是它**跑得太顺**：
worker 说「我把文件改好了」，引擎就真的把文件覆盖了，
**你原来写的东西没了，而你甚至没看见它被改成了什么。**

这条规则不是本项目发明的。MOKI（DeepSeek Harness 的本地资源管理器插件）
就是这条规则：**修改先进草稿，用户审核确认后再保存回原文件。**

MOKI 在**交互层**做这件事 —— 你选中一段文字，按 `Alt+D` 唤起 AI 对话，
改完先进草稿。本项目在**引擎层**做同一件事 ——
不管改动是模型提的、agent 提的、还是脚本提的，
只要它想覆盖一个已有的文件，它就**必须先变成草稿**。

---

## 草稿放在哪

草稿和它改的那个文件**住在同一个工作区里**，文件夹是 `.mas-drafts/`：

```
<state_dir>/artifacts/<run_id>/
├── deliverable.md          ← 交付物
├── notes.txt               ← 你的文件，原样不动
└── .mas-drafts/
    ├── D-1a2b3c4d.json     ← 草稿的元数据（含 diff）
    └── D-1a2b3c4d.data     ← 草稿的字节本身
```

**为什么不放在中心目录？** 一个住在中心目录的草稿，会在文件夹被复制的时候
一起丢失；而丢掉的草稿，是一份**永远没法被人审阅**的改动。

**为什么字节单独存？** diff 是**改动的报告**，不是**改动本身**。
批准的时候要写回的是 **worker 产出的那些字节**，所以字节也得存着。

---

## 草稿里有什么

每份草稿是一段 JSON：

| 字段 | 是什么 |
| --- | --- |
| `id` | 草稿编号（`D-` 开头） |
| `path` | 相对工作区的路径 |
| `state` | `pending` / `approved` / `rejected` |
| `reason` | 为什么提出这个改动 |
| `before_sha256` / `after_sha256` | 改动前后的哈希 |
| `before_bytes` / `after_bytes` | 改动前后的字节数 |
| `changed` | 是不是真的改动了（内容一样就是 `false`） |
| `diff` | 可读的 unified diff |

---

## 什么**不**走草稿

**新建文件照常直接写。** 一个还不存在的文件，
没有任何东西可以毁掉 —— 草稿规则是为了**不毁掉已有的工作**，
没有工作可毁的时候，规则就不该添乱。

所以 `mas drafts` 里出现的，永远是**对已有文件的改动**。

想回到旧行为，把配置里的 `edit_policy` 改成 `"overwrite"`：

```json
{ "edit_policy": "overwrite" }
```

**默认是 `"draft"`。**

---

## 机检看的是草稿里的字节

这是这一层最容易做错的地方。

**如果机检读的是磁盘上的旧文件**，那循环就会陷入死结：
它提一个改动 → 机检读旧文件 → 机检判不通过 → 循环改 → 再提一个改动 →
还是读旧文件……**永远闭不上**。

所以机检读的是**草稿里的新字节** —— 一个只存在于内存里的 overlay，
**不碰磁盘**。这样循环可以**用自己的提案闭合**：

> 批准与否，是关于**那个文件**的，不是关于**这次判定**的。
> 循环该跑完就跑完，文件该不该被改，由人说了算。

这和并行候选排序用的 overlay 是同一个想法。

---

## 边界

- **草稿只对工作区里的文件成立。** 工作区外的路径照旧被拒绝。
- **一份草稿只能批一次。** 批过之后再批会被拒。
- **驳回不会删草稿**，它只是把状态标成 `rejected` —— 人能看见
  「这份改动被看过、被否了」。
- **门禁 `draft_approval`** 盯着这一层：覆盖变成草稿、原文件字节不变、
  新建文件照常直接写、草稿带 diff、机检看到草稿字节、批准才写回、
  驳回一个字都不改 —— **八条变异全部被捕获**。

---

## agent 那一半：提议和批准分成两个动作（v0.7.73 起）

上面的规则管住了**引擎**。但一个会说话的 agent 拿着 MCP 工具，
本来可以直接改你的文件，**根本用不到草稿这一层**。

所以 MCP 上也有草稿工具，但**提议和批准不是同一个动作**：

| MCP 工具 | 做什么 | 能不能改文件 |
| --- | --- | --- |
| `mas_draft_stage` | **提**一份改动（带 diff 和理由） | **不能** —— 原文件一个字节都不动 |
| `mas_drafts` | 列出草稿、看某一份的 diff | 不能 |
| `mas_draft_resolve` | 批准或驳回 | **要人类令牌** |
| `mas_files` | 索引工作区 | 只读 |
| `mas_preview` | 预览一个文件 | 只读 |

### 人类令牌

```bash
mas drafts token        # 打印本机的人类令牌（存在 <state_dir>/human.token）
```

**令牌的作用不是保密，是分权。** 一个 agent 能拿到令牌吗？
能 —— 它和任何本地程序一样可以读那个文件。所以令牌**不是**一道墙，
它是一道**界线**：

- agent **提**草稿，不需要令牌（提议是安全的，因为文件没变）；
- agent **批**草稿，需要令牌。

这样「提议的人」和「确认的人」**至少可以是两个不同的角色**，
而不是同一个 agent 自说自话。令牌不对、空令牌、没令牌，
一律拒绝，而且**原文件不动**。

> 令牌文件的权限位在 POSIX 上是 `0600`；Windows 没有 POSIX 权限位，
> 那里靠 state 目录本身的保护。**令牌是障碍，不是围墙** ——
> 能读你本地文件的程序，本来就能改你的文件。

### 票据：人给出去的是一个决定，不是一把万能钥匙

令牌是**常备钥匙**：贴给 agent 一次，它就能批准**所有**草稿，
**永久有效**。在多智能体团队里这是一条真缝 ——
提议的人拿到了确认的权力，**分权就白分了**。

**票据**是窄门。`mas drafts ticket <草稿编号>` 用人类令牌签一张：

```bash
mas drafts token
# 记下这串令牌

mas drafts ticket D-1a2b3c4d --token <人类令牌>
# 输出：那一张票据本身（只出现这一次）
```

这张票据有四个性质：

| 性质 | 说明 |
| --- | --- |
| **绑定一个草稿** | 拿去批别的草稿 → `ticket_bound_to_another_draft` |
| **只用一次** | 第二次用 → `ticket_already_used` |
| **限时** | 15 分钟（`TICKET_TTL_SECONDS`）后 → `ticket_expired` |
| **只签一个动作** | 给驳回签的票据批不了批准 → `ticket_action_mismatch` |

**盘上不存明文**：票据库 `<state_dir>/tickets.json` 里只有
`sha256(票据)`。票据库被复制走，**也带不走一张能用的票据** ——
签发出来的票据只交到人手里一次。

用票据走 MCP：

```json
{
  "name": "mas_draft_resolve",
  "arguments": {
    "action": "approve",
    "draft_id": "D-1a2b3c4d",
    "ticket": "<那张票据>"
  }
}
```

没传票据时才回落到常备令牌。**票据不对时，报错会说明到底卡在哪** ——
而不是笼统一句「没有令牌」。

> 票据是**窄门**，不是**新的围墙**：能读你本地文件的程序，本来就能读
> 你的票据库。票据的作用是**缩小授权范围** —— 人给出的是
> **一个决定**，不是**做决定的能力**。

## 并发写冲突防护：两个人的活不会互相吃掉（v0.7.75 起）

草稿记下它**当时对着的那份文件**的哈希。人等草稿的这段时间里
改了文件 —— 批准下来，**人的新内容会被静默覆盖**。
两个 agent 抢一个文件时，这就是**丢失更新**：
团队最高频的事故，而且**一声不吭**。

这一版给写回装上**乐观锁**：不是锁住文件，是**写之前对一下**。

```bash
# 查哪些草稿的文件在等待期间被改过（不动任何东西）
mas drafts conflict
mas drafts conflict --json

# 批准：文件动过就被拒，磁盘上人的新内容原样不动
mas drafts approve D-1a2b3c4d

# 明知文件被改过，仍要写回
mas drafts approve D-1a2b3c4d --force
```

`mas drafts list` 和 `mas drafts show` 也会**标出**被移动过的草稿。

冲突时报的是**事实**，不是「不行」：

```json
{
  "error": "draft_conflict",
  "path": "notes.txt",
  "expected_sha256": "3bfc269594ef...",
  "current_sha256": "7d98d5e2d094..."
}
```

被拒的时候，**磁盘不动、草稿继续等**。
你可以改了文件之后再批准一次，也可以 `--force` 覆盖 ——
**明知故犯，得是人干的**。

### 票据不会被白烧

票据是**一次性的**。如果兑票在前、查冲突在后，
一次**注定失败**的批准会**烧掉人给的那一个决定** ——
票据没了，冲突还在，人得重新签一张。

所以顺序是反过来的：

```
peek_ticket()   看票，但不花
   ↓ 票对得上？
查冲突          文件动过？
   ↓ 没动过
redeem_ticket()  花票
   ↓
approve_draft()  写回
```

票不对、票过期、票对的是另一个草稿、票签的是驳回、文件动过 ——
**这五种情况票据都还在**。只有真正写回的那一次才烧票。

## 覆盖之前先看清会丢什么（v0.7.76 起）

冲突防护告诉你「**文件被改过**」—— 那是**事实**，不是**决定**。
人没法凭这句话判断那次改动值不值得留；要判断，得看见**改了什么**。

所以草稿现在**把基线一起存下来**（`<草稿编号>.base`，改动前的字节），
并把覆盖的代价摆到台面上：

```bash
mas drafts compare D-1a2b3c4d              # 基线 → 现在 → 草稿，三方对比
mas drafts compare D-1a2b3c4d --json
```

它会告诉你：

- **文件在等待期间被改过没有**（基线哈希 vs 现在的哈希）；
- **覆盖会丢掉哪几行** —— 你自己写的、草稿里没有的那些行；
  **没被改过的行不算丢失**；
- 两段 diff：**你写的改动**（基线 → 现在）和
  **草稿要写的改动**（现在 → 草稿）。

```text
草稿 D-1a2b3c4d  notes.txt
⚠ 文件在草稿等待期间被改过：期望 3bfc269594ef，实际 7d98d5e2d094。

覆盖会丢掉这 1 行（你写的，草稿里没有）：
  - human-added

--- 你写的改动（基线 → 当前） ---
+ human-added
--- 草稿要写的改动（当前 → 草稿） ---
- beta
+ beta-agent
```

**这个动作不改任何东西** —— 它是一份报告，可以反复看。

### 哈希基准被记下来

草稿现在记录 `digest_basis`。v0.7.76 之前记的是**解码后文本**的哈希，
而现在记的是**字节**的哈希 —— 两个数**不可混用**（对同一个文件，
BOM 或者被平台改写过的换行都会让两者不同）。

旧草稿改用**基线**比对；连基线都没有的旧草稿**不谎报冲突**
（`unknown_basis`）—— **假警报比没有警报更坏**，
它教会人忽略真警报。

### 二进制文件不被误判

不是 UTF-8 的文件**比不出逐行差异**。这时只比哈希，并且**不会**
被当成「已改动」；`compare` 会直说「比不出逐行差异，只能比哈希」，
而不是打印一堆乱码再称之为差异。

### 卡住的草稿要看得见

`mas_status` 增加 `conflicting_drafts` / `conflicting_draft_count`。
卡在冲突上的草稿是**人还欠的一个决定** —— 票据队列是给循环问问题用的，
不写进那里就等于**没人看见**。

### 门禁 `force_cost`

第 19 项门禁盯着这一层：草稿留下基线、对比点名会丢的行、
没改过的行不算丢失、无 force 仍被拒、命令行说得清、MCP 问得到、
二进制不被误判 —— 八个观察点。

判定被**独立实现了两遍**，两边必须一致才算过。

门禁还**自证能失败**：故意让「什么都不是丢失」变成「什么都是丢失」，
门禁必须报红。

### 门禁 `conflict_guard`

第 18 项门禁盯着这一层：草稿记住基线哈希、文件动过被察觉、
**人的新内容活下来**、冲突信息报出两个哈希、草稿**还在等**、
票据**没被烧**、命令行也拒、命令行也报哈希、
**只有显式 force 才覆盖** —— 十个观察点。

判定被**独立实现了两遍**，两边必须一致才算过。

门禁还**自证能失败**：故意让「什么都不是冲突」，
故意让「先写盘再问」—— 门禁必须报红。

**一个只能骗过产品、骗不过自己的门禁，不是门禁。**

### 门禁 `ticket_approval`

第 17 项门禁盯着这一层：票据要人类令牌才能签、错令牌签不出东西、
盘上不存明文、只对一个草稿生效、用一次就作废、过期即失效、
动作不匹配被拒、无令牌无票据一律不开门 ——
**十三个变异全部被捕获**（其中四个是**门禁自己的判定被改坏**）。

判定被**独立实现了两遍**，两边必须一致才算过。

### 门禁 `mcp_draft_approval`

第 16 项门禁盯着这一层：MCP 广告了这三个工具、agent 能提草稿、
原文件不动、草稿带 diff 和理由、**没有令牌批不了**、**错令牌也批不了**、
对令牌才写回、驳回一个字都不改、MCP 能索引能预览 ——
**十条变异全部被捕获**。

这道门禁的判定被**独立实现了两遍**，两边必须一致才算过：
改坏判定函数本身，会被对照的那一份当场抓住 ——
**一个只能骗过产品、骗不过自己的门禁，不是门禁**。

## 批错了还能退回来（v0.7.77 起）

草稿层把**批准**变成了改动到达文件的**唯一**通道 —— 但它也让批准变成了
**一扇单向门**：人批错了，唯一的退路是**手工去改文件**。
而草稿里明明存着改动前的基线（v0.7.76 起），**却没人能用它**。

现在这一步补上了：

```bash
mas drafts undo D-1a2b3c4d              # 把这次改动收回来
mas drafts undo D-1a2b3c4d --json
```

- **逐字节退回** —— 文件回到草稿建立时的样子，**不是**近似、不是反向 patch，
  是把当初存下来的基线原样写回去。
- **草稿还在** —— 撤销之后草稿回到可批准的状态（`undone`），
  同一个改动**还能再批准一次**。想清楚为什么撤销之后，随时可以再来一遍。
- **撤销也会先问代价** —— 如果文件在**批准之后**又被人改过，
  撤销会**拒绝**，并且**点名会丢掉哪几行**：

```text
文件在批准之后又被改过，撤销被拒：批准时 cdf843f6332b，现在 e7a872fcc345。
文件保持现在的内容不变；确认要连这些改动一起退掉就用 --force。

撤销会丢掉这 1 行（批准之后才写进去的）：
  - human-after-approval
```

**这是一条对称的规则**：批准会挡住「覆盖掉别人更新的文件」，
撤销会挡住「抹掉批准之后的新工作」。两者都把代价摆出来，
都由**人**决定，不由机器替人决定。

### agent 那一半

MCP 多了 **`mas_draft_undo`** —— 和 `mas_draft_compare` 一样，
agent 问的是同一个问题、拿到的是同一个答案：

```json
{
  "draft_id": "D-1a2b3c4d",
  "token": "……",
  "force": false
}
```

它同样**需要人类令牌或一次性票据** —— agent 能提草稿、能问代价，
但**改一个已经写进文件的决定，得是人干的**。

### 门禁 `undo_guard`

第 20 项门禁盯着这一层：撤销把文件逐字节退回、草稿撤销后仍在、
没批准的草稿不能撤、批准后文件又变过就拒绝撤销、拒绝时说清代价、
命令行能撤、agent 问得到 —— **七个观察点**。

判定被**独立实现了两遍**，两边必须一致才算过。

门禁还**自证能失败**：故意让撤销写错字节，门禁必须报红。

### `mas_status` 看得见撤销

```json
{
  "undone_drafts": [
    {"draft_id": "D-1a2b3c4d", "path": "notes.txt", "undone_at": "……", "note": "批错了"}
  ],
  "undone_draft_count": 1
}
```

一个被撤销的改动**不是「还没发生」**：它说明**有一次批准是错的**，
而那份草稿还在原地，等着被批准第二次。

## 撤销事件进账本，改过的痕迹查得出来（v0.7.78 起）

撤销到这一步为止，还只是一个**文件操作**：文件退回去了，但机器自己的
记录里看不出「这次批准后来被撤回了」——那条线程看起来和一次普通的批准
毫无区别。

「一次批准是错的」这件事，现在**在审计里留痕**。

### 写两遍

每一次**批准**和**撤销**都写两个地方：

1. **链式审计链** —— `<工作区>/.mas-drafts/audit.jsonl`
   每条记录长这样：

   ```json
   {"event": "draft_undo", "ts": "...", "seq": 3,
    "prev_sha256": "<上一条的哈希>", "sha256": "<自己内容的哈希>",
    "draft_id": "D-1a2b3c4d", "path": "notes.txt", "note": "批错了"}
   ```

   `sha256` 覆盖**上一条的哈希 + 自己内容**。所以：
   - 改一条内容 → 它自己的 `sha256` 对不上；
   - 删一条 → 后一条的 `prev_sha256` 和序号对不上。

2. **主账本** —— `mas ledger` 看得见的那本，同样带着
   `audit_sha256` / `audit_prev_sha256` 和被复制的字段。

### 检查

```bash
mas audit                              # 检查默认工作区
mas audit --workspace <路径>            # 检查指定工作区
mas audit --workspace <路径> --json     # 机器可读
```

有问题时**退出码是 1**，并且**指名**是哪里：

| 手法 | 报出来的话 |
| --- | --- |
| 改链里一条 | 第 2 条的内容被改过 |
| 删链中间一条 | 第 2 条的序号是 3（应为 2）／第 3 条与上一条的链接断了 |
| 只改账本副本 | 账本与审计链不一致：D-xxx 的 note |
| 删账本副本 | 审计链里的记录（D-xxx）没有进账本 |
| 账本里多一条 | 账本里的撤销（D-xxx）在审计链里找不到对应事件 |
| **什么都没动** | **不报** —— 干净链必须零误报 |

两份副本是按**逻辑身份**对上的（哪个工作区、哪个草稿、哪一种决定、第几次），
**不是**按哈希。哈希是**被比对的那一项**，不是**键**——
否则一条被改过的记录会先「找不到」，真正的「被改过」反而说不出来。

链上比账本多一条**提案**（`draft_stage`）——它不是人工决定，不进账本，
但**不会打乱**两边对决定的编号。

### 诚实的边界

一条链**不是公证**。把整条链从被改的那条起重写一遍，它会重新「验证通过」——
链外没有任何东西记得原来的头是什么。

所以决定写了两份，两份要一致。这检测的是**改一条、删一条、只改一份副本**，
**不是**有人把两份一起重写。

还有一条边界：**删掉链的最后一条**，链本身仍然自洽（后面没有记录指着它），
这一条由**账本副本**抓出来 —— 这也是「写两遍」真正的用处。

## 和 MOKI 的关系

| | MOKI | 本项目 |
| --- | --- | --- |

规则是同一条。
