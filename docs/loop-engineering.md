# Loop Engineering：多智能体循环怎么才算闭合

## 一句话

**闭合 = 有一个可被机器判定的结束条件，并且这个判定被记录下来。**

没有这一条，多智能体系统就是一台「烧 token 的永动机」。

## 四个常见的不闭合症状

| 症状 | 表现 | 本项目的对应机制 |
| --- | --- | --- |
| 无验收标准 | 「我觉得差不多了」 | `criteria` 必填，且支持机检规则 |
| 无退出条件 | 一轮轮往下聊 | 闭合/升级/预算三种终态，二选一必须发生 |
| 无过程记录 | 出事无法复盘 | append-only 账本，每轮一条 |
| 无止损 | 走不通的任务反复重试 | 迭代/墙钟/token 三重预算 + 停滞检测 |

## 关键区分：谁的判定

一个循环能不能闭合，取决于**判定权在谁手里**。

- 判定权在模型手里 → 模型说「好了」就是好了，无法复现，无法审计；
- 判定权在引擎手里 → 同一份产物 + 同一份标准，永远得到同一个结论。

因此本项目把验收标准拆成两层：

```
验收标准
├─ 带 check  →  引擎判定（contains / min_chars / regex / json_keys ...）→ 可复现
└─ 无 check  →  模型判定（verifier 给出 pass/note）→ 不可复现，但仍然要给出证据
```

两层都通过才算闭合；模型层没给结论的，按不通过处理。

## 第三层：证据必须来自磁盘（v0.7.15）

前两层还有一个共同的前提没被检验：**模型的产物文本本身也是模型写的**。
所以「产物里写着 `out/report.md` 已生成」和「`out/report.md` 真的在磁盘上」，
在文本机检眼里是同一件事。于是有一类闭环看起来闭合了，实际只是**承诺被当成了事实**：

> worker 说「已把结论写入 `out/report.md`」，产出一段很像样的说明；
> 机检搜文本 → 找不到期望字符串 → 不通过；可一旦期望字符串也出现在那段说明里，
> 机检就判通过——**而磁盘上根本没有那个文件**。

所以 v0.7.15 加了第三层：

```
验收标准
├─ 带 check  →  引擎判定（文本层）
├─ 无 check  →  模型判定（语义层）
└─ 文件级 check →  引擎判定（磁盘层：file_exists / file_contains / file_sha256 ...）
```

磁盘层的判定权**不在模型手里**：文件在不在、字节是多少、摘要是什么，
都是引擎自己去 `stat` 和 `read` 出来的。模型说了不算。

配套还必须有**写侧**：worker 的输出只是一个字符串，它没有别的途径把文件放到磁盘上。
v0.7.15 的写文件协议给了它一条有限、可审计的路——
`<<<MAS:FILE path="...">>>` 围栏块，引擎原样落盘、记账本、拒越界。

只加读侧不加写侧是半个功能（检查永远过不了）；只加写侧不加读侧更危险
（写了也证明不了，只是多了一个能乱写文件的口子）。两层必须一起上。

详见 [`file-checks.md`](file-checks.md)。

## 「机检标准」的写法

一条好标准的特征是：**读者和机器都能独立判定它成立与否。**

| 反例（不可核验） | 正例（可核验） |
| --- | --- |
| 质量要好 | 正文 ≥ 800 字且包含 3 个小节标题 |
| 不要有错别字 | 不包含 `TODO`、`待补充`、`xxx` |
| 结构清晰 | 存在 `## 背景`、`## 方案`、`## 验收` 三个标题 |
| 数据要准确 | JSON 中的 `version` 字段等于 `v0.1.0` |

写不出机检规则，往往说明**目标本身还没想清楚**。这时正确动作不是硬编一条规则，而是把目标拆细，或者接受「这条标准交给模型判定，但要求它给出证据」。

## 闭环的四个不变量

1. **闭合必须可判定**：`status` 只有 `closed` / `escalated` / `budget_exhausted` / `error`。
2. **闭合必须留痕**：闭合的那一轮一定有 `closure` 账本条目，含产物哈希与逐条判定。
3. **不判定不放行**：没有判定 = 不通过。
4. **停不下来就升级**：停滞与预算触顶都要升级人工，而不是继续空转。

## 第六个不变量：闭环必须钉在它判定时依据的字节上（v0.7.88）

前面五条不变量管的是**判定怎么发生**。这一条管的是**判定之后**。

一个闭合的循环声称：**同一份产物 + 同一份标准，永远得到同一个结论。**
但这个承诺只兑现了一半：

* 账本记了交付物**正文**的哈希，**验收标准却只活在引擎的内存里** ——
  事后的读者**没法独立重算**，只能选择相信；
* worker 写出的文件只记了**长度**，没记内容 ——
  事后有人把文件改掉（哪怕改回**同样长度**），账本**一点察觉都没有**，
  循环照样报 `closed / pass`。

这两条是同一个洞：**结论没有被钉在它判定时依据的那份字节上。**
「结论可以重算」这句话，当时只是**关于引擎内部**的；它从来没有
**对账本**成立过。

所以闭环在判定的那一刻，把**它判定所依据的东西**一起封进账本：

```
封存 = {
  完整的验收标准,      # 重算的输入
  交付物的 sha256,      # 重算的输入
  每个写出文件的 sha256, # 事后有没有被改
  逐条判定,            # 重算的结果要和它比对
  判定结论 / 决策 / 工作目录
}
```

之后 `mas seal` 只凭这份封存**重新推导**结论：重读磁盘、重跑机检、
拿结果和封存的判定比对。

### 三条边界，说清楚它证明到哪一步

1. **只由模型判定的标准不能重算。** 模型判过的标准会被封成模型的答案，
   并如实标成 `model-judged` —— **不谎称重算过**。
   封存因此证明的是「**有机检的那部分仍然成立**」。
2. **不能重算不算通过。** 交付物不在了、格式读不懂了，都报成
   `unrecomputable`，**不是** `pass`。
3. **封存是记录，不是公证。** 同时改掉封存和账本的人仍然能造出一份
   能通过复核的封存。它换来的是：**一次普通的事后小改动会变得可见**。

### 三条闭合路径，封存得一样严

主循环、人工交付物（`handback`）、人工文件夹交付（`handback_workspace`）
是三种闭合，判定的标准都是同一套，所以封存也是同一套。

这一点不是一开始就对的 —— 写这一格的时候当场抓到**两个真 bug**：

* 两条人工路径在封存时引用了一个**并不存在**的变量：
  交付物判完了、文件写好了，运行却在写账本的路上**崩掉**；
* 封存记的是**运行自己的目录**，而机检读的其实是**人工编辑的那个目录** ——
  重算读到另一个文件夹的文件，**把没发生过的漂移报成漂移**。

两个都没有测试钉住，因为**没有一个测试向人工路径要过封存**。

### 这条不变量由第 28 项门禁 `closure_seal` 守着

```bash
mas selftest --only closure_seal
```

门禁要求：闭环**确实带上封存**、封存**确实能重算出同一个判定**、
文件被改过**确实被说成漂移**、封存被改过**确实被说成篡改**、
**不能重算的不算通过** —— 而且门禁自己**必须能失败**：
它会把漂移检测故意打断一次，然后确认自己**注意到了**。

## 第七个不变量：结论漂移了，报告必须说出来（v0.7.89）

第六个不变量让结论**可以重算**。
但“可以重算”有两个实现的地方：

* `mas seal` —— 一个**专门的命令**，给出“这些闭环还成立吗”的答案；
* `mas report` —— **人真正会看的那个屏幕**。

在 v0.7.89 之前，**第二个地方不存在**。
报告从来不看封存，所以它继续写“已解决”、
“机器闭环”，屏掉一个**结论的字节已经被改过**的闭环。

这是一个很具体的失败：

* 用户跑完一个任务，看报告：“已解决。”
* 两天后他修了一下交付物里的文件。
* 再看报告：**仍然是“已解决。”**。

**能证明漂移的能力，却没有被主视图消费 —— 那就等于没有。**

### 报告里多了什么

| 位置 | 之前 | 现在 |
| --- | --- | --- |
| 问题概览的状态列 | 已解决 | **结论已漂移** |
| 运行概览的状态列 | `OK 已闭环` | `DRF 结论已漂移（已闭环）` |
| 运行概览的来源列 | 🤖 机器闭环 | **⚠ 结论已漂移** |
| 报告顶部 | 只说闭环率 | 多一行“封存复核：N 条封存中…” |
| 每个运行的详情 | 没有 | **封存：⚠ 结论已漂移** + 哪个文件被改过 |
| JSON 载荷 | 没有 | `seal: {sealed, holds, drifted, ok, states}` |

**封存不存在的运行不被报成漂移。**
封存是 v0.7.88 才加的，就算靠现的旧闭环没有封存，
它也**不是被改过的**。“没有封存”和“封存漂移”
是两件事，报告分得开。

### 为什么不能只做到 `mas seal`

可以，`mas seal` 已经能答这个问题了。但它是一个
**专门命令**，一个专门命令能做的事，**主视图不做就等于没有**。

而且这里还有一个细节：**报告是一个几万行的文本**。
一个人会自然先扫“问题概览”那记表 ——
**所以漂移必须出现在那里**，而不是只在运行详情里。
本版本就是这个原则：**漂移在摘要表里就看得见。**

### 这条不变量由第 29 项门禁 `report_seal` 守着

```bash
mas selftest --only report_seal
```

门禁要求：健康的闭环被报成“仍然成立”、
被改过的闭环在**问题概览**、**运行概览**和
**运行详情**里都说出“结论已漂移”、
JSON 载荷里带上复核结果 —— 而且门禁自证**能失败**：
它会把报告的封存检查故意打坏成“永远成立”，
然后确认自己已经**分不出**健康的闭环和被改过的闭环。

## 第八个不变量：一次批准是错的，这件事在报告里必须说得出来（v0.7.90）

第七个不变量让“结论漂移”可见。
但还有一类事实，它不是关于运行的，而是关于**人的决定**：

* 你批准了一个草稿（`draft_approve`）；
* 你发现它是错的，把批准撤回去（`draft_undo`）；
* 文件被退回去了，账本里留下了痕迹。

**你的批准曾经是错的——这一点还记得着。**
但在 v0.7.90 之前，`mas report` 从来没看过它：
`run_summary()` 根本不读 `draft_approve` / `draft_undo` 那两类行。

这里有一个很具体的失败：

* 你运完一个任务，看报告：「已解决 · 机器闭环」。
* 三周前你撤回过两次错批准，账本里醒着。
* 再看报告：**还是「已解决 · 机器闭环」**。

你看到的是一个干净的机器，背后却是一段**错的历史**。

**能证明「哪些批准是错的」能力，却没有被主视图消费 —— 那就等于没有。**
（与第七个不变量同型：能力存在，主视图不消费。）

### 撤销属于工作区，不属于任何一次运行

这里有一个容易造成脏数据的地方：
**草稿和运行之间没有关联键。**
同一个草稿可以被批准、撤销、再批准，
自始至终没有任何一次运行参与过。

所以“把它塞进某个线程”会**凭空造出一个关系**，
而“塞进某次运行”同样是假的。
它是**工作区级的事实**，所以报告把它放在
**报告顶层**、单独一节，不硬塞进任何一次运行。

### 报告里多了什么

| 位置 | 之前 | 现在 |
| --- | --- | --- |
| 报告顶部 | 没有 | **撤销回收：N 次批准被撤销** |
| 报告正文 | 没有 | **「被撤销的批准」**一节（草稿 / 文件 / 次数 / 退回行数） |
| JSON 载荷 | 没有 | `undos: {records, unmatched, totals, drafts}` |
| 顶部计数 | 没有 | `approvals_taken_back` / `drafts_taken_back` / `lines_reverted` / `undos_unmatched` |

**只有人工决定、没有任何运行的账本，不再被说成「账本为空」。**
这是一句假话：账本里满是错批准。
现在这个情况会说「这台机器上还没有跑过任何一次闭环，
但账本里记着人工的决定」，并指向 `mas undos`。

### 配对逻辑不重写

`mas.undos` 已经把配对做对了（位置式栈，
撤销取回**最近一个还立着的批准**）。
报告只是**读**这个答案，不重新实现一质。
因此**配不上的撤销被计数而不隐藏**（报告顶部会单独说出来），
而且**不猜**。

### 这条不变量由第 30 项门禁 `report_undo` 守着

```bash
mas selftest --only report_undo
```

门禁采用**双读法**：一条读报告，
另一条**绕开报告**、直接数账本行里的批准/撤销配对，
两边必须一致。门禁还**自证能失败** ——
把报告的撤销计数打坏成「永远等于合法」，
门禁必须发现它已经分不出错批和对批。

## 第九个不变量：记录被篡改了，报告必须说出来（v0.7.91）

第八个不变量让「你的批准曾经是错的」可见。
但还有一类事实，它不是关于**一次决定的对错**，
而是关于**记录本身有没有被改过**：

* 你批准了一个草稿 → 链里一条哈希相连的记录；
* 你把批准撤回去 → 又一条；
* 有人用编辑器改了其中一条的 `note` → **链不再自洽**。

**你的决定记录被改过了 —— 这一点还记得着。**
但在 v0.7.91 之前，`mas report` 从来没看过它：
`mas/report.py` 的 `import` 里连 `mas.audit` 都没有。

这里有一个很具体的失败：

* 你运完一个任务，看报告：「已解决 · 机器闭环」。
* 有人改过你的审计链（或者删了整条链）。
* 再看报告：**还是「已解决 · 机器闭环」**。

**能证明「记录没被改过」的能力，却没有被主视图消费 —— 那就等于没有。**
（这是同型洞的第三个：封存、撤销、审计链。）

### 报告怎么找到要查的链

**从账本行自己反推，而不是猜目录。**
每一行带 `workspace` 字段的记录都知道自己属于哪个工作区，
报告就查**写下那些决定的那几条链** —— 不多不少。

`mas status` 是猜 `<state_dir>/artifacts` 的。
报告若也这么猜，就会漏掉那些自带工作区的运行，
也会去读不属于任何人的链。**报告比 status 更精确。**

### 链整个不见了，怎么发现

一条被**整体删掉**的链，读它是读不出问题的 —— 没有内容可读。
但**账本里还留着那个决定**，所以报告会把

> 工作区 X 的账本记着 N 条人工决定，但审计链不见了

当成一个**记录缺口**点出来。
**缺失也必须被说出来** —— 否则删链就成了最省事的掩盖办法。

### 报告里多了什么

| 位置 | 之前 | 现在 |
| --- | --- | --- |
| 报告顶部 | 没有 | **审计链复核：N 条链、M 条记录，K 个问题** |
| 报告正文 | 没有 | **「审计链复核」**一节（逐条点名哪个链、哪条记录被改过） |
| JSON 载荷 | 没有 | `audit: {workspaces, chains, chain_count, entries, problems, problem_count, ok}` |
| 顶部计数 | 没有 | `audit_chains` / `audit_entries` / `audit_problems` |

**退出码语义不变。** 报告仍然以 0 退出 ——
报告是给人看的，**报警的出口是 `mas audit` 和 `mas seal`**。

### 这条不变量由第 31 项门禁 `report_audit` 守着

```bash
mas selftest --only report_audit
```

门禁采用**双读法**：一条读报告的 Markdown，
另一条**绕开报告**、直接读 JSON 载荷里的链和问题，
两边必须一致。门禁还**自证能失败** ——


## 第十个不变量：自检不得污染被它检查的那台机器（v0.7.92）

前面九条不变量都在讲**运行时**。
这一条讲的是**检查运行时的那段代码**本身。

自检要证明「撤销是真的把文件退回去了」，
所以它**必须真的批准一次草稿、真的撤销一次**。
而「批准」是一次**人工决定** ——
人工决定要记进**主账本**。

于是（v0.7.92 之前）：

```
mas selftest  →  ~/.mas/ledgers/runs.jsonl 多出若干行
                 workspace 指向一个当场就被删掉的临时目录
```

行留下了，**链没了**。于是：

```
mas report →  账本说「人批准过什么」
              链说「没有这条链」
              → 报出几百个审计问题
```

**那几百个「批准」是测试自己批的。**
用户跑过一次自检，这台机器就会**永远**报几百个问题，
而且**分不出**哪个是真问题、哪个是测试留下的。

> **一次会改变被测机器状态的自检，不是自检 —— 它是一个带退出码的副作用。**

### 三条边界，说清楚它证明到哪一步

| 边界 | 含义 |
| --- | --- |
| **账本行数与字节都不变** | 不是「差不多一样」，是**行数一致、文件摘要一致** |
| **环境变量原样还原** | 一道门禁改了 `MAS_STATE_DIR` 却没改回去，就会**悄悄重指向后面所有门禁**，把下一个泄漏盖住 |
| **自检的决定仍然被记录** | 隔离不能顺手把记录也丢了 —— 否则证明「审计链有效」的那几道门禁**等于什么都没证明** |

第三条是这一条不变量最容易做错的地方：
**隔离不是遗忘**。记录要留在**测试自己的**账本里。

### 套件级兜底

除了逐门禁隔离，整轮自检**前后**还会对比机器的状态目录：

* 任何落在临时目录之外的改动 → **被点名**；
* 并且**让整轮自检失败**。

这样以后**新增**的门禁即使忘了隔离，也会被立刻抓住 ——
而不是等它在用户机器上跑了几百轮之后。

### 这条不变量由第 32 项门禁 `selftest_isolation` 守着

```bash

```

门禁**自证能失败**：把隔离打坏成「什么都不隔离」，
门禁必须发现它已经分不出「干净的一轮」和「脏的一轮」。

## 第十三个不变量：文档还是文本（v0.7.94）

写 v0.7.93 发布说明时，文本是经过一个把反引号当**转义符**的 shell
产出来的。所以：

| 写的是 | 得到的是 |
| --- | --- |
| `budget` | 一个**退格符** |
| `tickets` | 一个**制表符** |
| `reason_text` | 一个**回车**，后面的 `eason_text` 又少了首字母 |
| ```bash | ``bash |

伤害很小，而且在渲染后的 Markdown 页面里**几乎看不出来**：
句子还是那个句子，代码块还像个代码块。
但**磁盘上的文件已经坏掉了** —— 字母的位置上是一个控制字符，
缩进的地方是一个 Tab。

而它**发布出去了**，因为**没有任何东西在看**。

这正是关键。一份文档是初学者第一个打开的文件。
一份里面带退格符的文档不是文档，
它只是一个**大致是文本**的文件。

而本项目自己的规则是：**没人检查的能力，就算没有** ——
所以这个项目里的每一个坑都有一道门禁，这一个也在等。

### 这条不变量说了什么

| 边界 | 含义 |
| --- | --- |
| **没有控制字符** | 退格符、裸回车、其他控制字符 —— 都不是文本 |
| **没有残留的 Tab** | 附言里的 Tab 是被吃掉的字符；围栏里的 Tab 可以容忍 |
| **代码围栏完整** | 开头围栏只能写语言（或不写），闭合围栏不能带文字，每个围栏都要有尾 |

### 为什么这条需要门禁

不是因为"规范"。是因为"规范"**已经无声地破坏过一次**，
并且破坏的方式是"把字母吃掉" —— 这个方式在渲染后看不出来。

所以门禁不只看"有没有异常"，它还要**自证能失败**：
把一份文档**故意破坏**（注入一个退格符），
门禁必须发现它已经分不出"正常文本"和"被磨损的文本"。

## 第十四个不变量：复盘报告必须读每一条账本行（v0.7.95）

账本是真相，报告是账本的投影。
但投影**漏掉了六种行** —— 于是报告读出来的账本，
比实际的账本**少了一半内容**。

账本表的最后一列叫「摘要」，内容来自 `mas/report.py` 的 `_short_detail()`。
它按角色分派：`closure`、`planner`、`review`、`reflector`、`handback`、
`draft_approve`、`draft_undo`…… **有六个角色根本没有分支**：

| 角色 | 它记录的是什么 | 之前渲染成 |
| --- | --- | --- |
| `write` | 引擎实际写了哪些文件、多少字节、新建还是覆盖 | **空白** |
| `draft` | 循环提议了哪个改动、等人批 | **空白** |
| `truncated` | 回答写到一半被截断，所以要重试 | **空白** |
| `reask` | 因为哪几条标准没过而补问 | **空白** |
| `reask_failed` | 补问失败了 | **空白** |
| `lead` | 顾问给出的建议 | **空白** |

分派落到最后是 `return ""`。
表格里那一行**在** —— 有序号、有时间、有运行号、有角色 ——
唯一说「发生了什么」的那一列**是空的**。

### 为什么这一条特别要紧

`write` 行是唯一一行能回答
**「这个智能体到底改了我机器上的什么」** 的记录：
哪个文件、多少字节、是新建还是覆盖。

而它在报告里**完全看不见**。

于是：**写了三个文件的运行，和什么都没写的运行，在报告里长得一模一样。**

一个审计者打开报告，看到「闭环了，通过 3/3」，
他知道交付物是对的；他**看不到**这三个文件是哪三个、
也没法确认引擎有没有顺手改了他没要求改的东西。

这和前五个洞是同一个家族 ——
**能力存在，主视图不消费**：

| 版本 | 能力 | 之前的状态 |
| --- | --- | --- |
| v0.7.89 | 封存 | 报告不看 |
| v0.7.90 | 撤销 | 报告不看 |
| v0.7.91 | 审计链 | 报告不看 |
| v0.7.93 | 工单队列 | 报告不看 |
| v0.7.94 | 草稿队列 | 报告不看 |
| v0.7.95 | **每一条账本行** | **报告不看** |

### 这条不变量说了什么

| 边界 | 含义 |
| --- | --- |
| **每种角色都要有话说** | 引擎写得出的每一种行，摘要都**非空** |
| **写入要点名** | 文件名、字节数、新建 / 未写入；一次都没写成时说「没有文件被写入」，不留白 |
| **草稿要点名** | 草稿号与文件 |
| **截断要点名** | 截断的原因、已用 tokens、将重试 |
| **补问要点名** | 哪几条标准没过 |
| **顾问要点名** | 顾问说了什么 |

`role_reading()` 也补上了 `draft` 的中文读法「提议改动」——

```bash

```

门禁读**引擎会写出的每一种账本角色**，要求每一种的摘要都非空，
而且**导出的表格里没有任何一行摘要为空**。

## 第十五个不变量：交付物清单必须同时到达命令行和 MCP（v0.7.96）

### 洞在哪里

### 这条不变量说了什么

## 第十六个不变量：闭合的判定必须同时到达命令行和 MCP（v0.7.97）

`mas doctor` 只体检配置。`mas run` 只跑一次任务。**MCP 里没有任何一个工具能回答「这套系统闭不闭合」**——而这正是 LoopEngineering 自己的核心命题。

### 洞在哪里

报告能展示所有数字：跑了多少次、闭合率多少、有几张工单在等人、有几份草稿没批。

但**「闭合」的判定规则从来没被写下来放到读者够得着的地方**。拿着整套 MCP 工具的智能体读完报告的所有数字，仍然得**自己**在脑子里把这几格拼起来，才能回答「这活儿干完了吗」——而不同的人拼法不一样。

换句话说：报告**展示**闭合，判定**不存在**。一个能把每一个数字都摆出来的系统，不一定知道自己算不算完。

### 这条不变量说了什么

| 边界 | 含义 |
| --- | --- |
| **一份判定，两个界面** | 判定住在 `mas/report.py`：`closure_verdict()` 算，`format_closure()` 渲染，`closure_verdict_for()` 是两个界面共用的唯一入口 |
| **闭合 ≠ 跑成功** | 闭合是「没有任何东西在等」：没有未闭合的运行、没有开着的问题线索、没有等人工接手的工单、没有等人批准的草稿、没有对不上的封存、没有验不过的决策链 |
| **每一格单独报数** | 只说「没闭合」是把读者撵去自己找；说「3 份草稿等人批准」才告诉他该干什么 |
| **空账本不算闭合** | 账本是空的不是「闭环完美」，是「还没跑过」——这两种情况必须用不同的措辞，冒充就是撒谎 |
| **只读** | 判定读账本、读工单队列、读草稿队列；它**不启动任何一次运行** |

新工具 `mas_closure`（MCP），新命令 `mas closure`（命令行，未闭合时退出码 2）。

| v0.7.93 | 工单队列 | 报告不看 |

| v0.7.95 | 每一条账本行 | 报告不看 |

| v0.7.97 | **闭合的判定** | **两个界面都没有** |

## 第十七个不变量：闭合的粒度是问题，不是尝试（v0.7.98）

v0.7.97 把闭合判定放进了 `mas/report.py`，命令行和 MCP 共用一份。这一条是它的**续集**：
判定住下来了，但**数错了东西**。

### 洞在哪里

报告把运行按**问题**分组：一次失败后被 resume 成功的问题，是**一个问题**，
闭合了。线程判定的规则一直是对的——**最后一次尝试说了算**，后来的尝试取代前面的。

可是闭合判定数的是 `totals["not_closed"]`，也就是**没闭合的尝试数**。
于是同一份报告能同时说两件事：

```
threads:    [('T-1', closed=True)]        <- 问题已闭合
VERDICT:    ok=False ['runs_not_closed']   <- 还有东西在等
```

**一份报告，两个答案。**

更要命的是后果：**失败 → resume → 成功**这条核心工作流，永远拿不到 `ok=True`。
问题队列只会越积越多，而一个永远不清空的队列，教会读者忽略它——
这正是这个项目一直在修的那类失败，换了个马甲。

### 这条不变量说了什么

| 边界 | 含义 |
| --- | --- |
| **粒度是问题** | 一次失败后被成功尝试**取代**，问题就是闭合的 |
| **历史不是待办** | 被取代的失败仍然计数，但不算「还在等」 |
| **一份报告一个答案** | 报告的线程判定和闭合判定不能对同一个问题说出相反的话 |
| **两个闭环率，两个粒度** | 尝试闭环率和问题闭环率**各自报出自己的粒度**，不混着说 |

### 三个数，各有各的用处

| 数 | 是什么 | 例子（失败→成功） |
| --- | --- | --- |
| `not_closed` | **所有**没闭合的尝试。历史。 | 1 |
| `not_closed_open` | **仍在开放问题里**的失败尝试。待办。**判定建在它上面。** | 0 |
| `not_closed_superseded` | 已被后来成功尝试取代的失败。历史的一部分。 | 1 |

另外新增 `problem_closure_rate`（已解决问题 / 全部问题），
和原有的 `closure_rate`（已闭合尝试 / 全部尝试）**并存**——
一个是问题的闭环率，一个是尝试的闭环率，读者一眼能看出差在哪。

### 这是同一族的第九个洞

前八个的形状是「能力在账本里，主视图不读它」「能力在一个界面里，另一个界面看不见」
「判定规则只存在于人的脑子里」。这一次的形状是：**判定存在了，但数错了粒度，
于是报告自己跟自己打架。**

| 版本 | 能力 | 之前的状态 |
| --- | --- | --- |
| v0.7.89 | 封存 | 报告不看 |
| v0.7.90 | 撤销 | 报告不看 |
| v0.7.91 | 审计链 | 报告不看 |
| v0.7.93 | 工单队列 | 报告不看 |
| v0.7.94 | 草稿队列 | 报告不看 |
| v0.7.95 | 每一条账本行 | 报告不看 |
| v0.7.96 | 交付物清单 | MCP 看不到 |
| v0.7.97 | 闭合的判定 | 两个界面都没有 |
| v0.7.98 | **闭合的粒度** | **报告和判定互相打架** |

```bash

```

门禁要求：被取代的失败**不占着队列**、最后失败的问题**仍然开着**、

## 第三十三条不变量：人批准过的改动，不是漂移（v0.11.2）

前三十二条不变量都在管**判定怎么发生**、**判定之后怎么被看见**。
这一条管的是**指控的分寸**。

### 洞在哪里

第七个不变量让「结论漂移了」可见。这是闭环里最响的一个警报 ——
因为漂移说的是**「这次运行对它从未说过的话撒谎」**。

可有一种改动根本不是这样：**人审阅了交付物，批了一个改动，
改动写回了磁盘**。这是闭环**该有的样子**，不是对闭环的攻击。

而在 v0.11.2 之前，封存复核只有**一个词**可以用来描述
「运行闭合之后这个文件又变了」：**漂移**。

于是最常见的正常工作流，被报成了最严重的指控：

    人批准一个改动 -> 改动落盘 -> 封存复核发现字节对不上 -> 报「结论已漂移」

那次批准**是有记录的** —— 它躺在哈希链接的审计链里，带着它写下的
那些字节的哈希。复核**从来没问过**「这是谁改的」。

### 这条不变量说了什么

| 边界 | 含义 |
| --- | --- |
| **人批准过 != 有人偷改** | 一次合法批准之后的改动叫**人工接手**（`taken-over`），不叫漂移 |
| **结论仍然成立** | 接手是**换人继续做**，不是推翻结论 —— 状态 `ok=True` |
| **没批准的仍然是漂移** | 锁没有被削弱：无人认领的改动照旧报警 |
| **批准得对得上** | 同一文件夹、同一文件、同一批字节 —— 三样都对得上才算 |
| **撤销过的不算** | 被拿回去的批准不背书 |
| **链坏的不算** | 审计链验不过时，这个文件夹里**一条批准都不采信** |
| **每一面说同一件事** | 报告、命令行、状态页与 MCP 对同一个封存给出同一个状态 |

### 证据从哪儿来：审计链是权威源

批准记录有两个可能的地方：主账本，和**哈希链接的审计链**。
这一版把审计链定为权威源：

* 链**存在**且**验得过** -> 以链为准；
* 链**存在**但**验不过** -> 这个文件夹里**什么都不采信**
  （验不过的批准不能拿来豁免任何改动）；
* 链**不存在**（链出现之前的老工作区）-> 回退到账本行。

只有一个面握着**整本账本**是不够的 —— 报告面只有「一次运行的那些行」，
状态页只有「一枚封存」。所以 `approvals_in_workspace()` 让它们
**自己去这个文件夹的链上取证**，这样同一个封存在每一面读出来的状态一致。

### 顺带撞见的另一个同族 bug

`verify_seal()` 原本拿**交付物文本的哈希**去比**批准记录的字节哈希**。

这不是一回事。只有在**不重写换行**的机器上（Linux / macOS）
两个数才碰巧相等；Windows 的 `write_text` 会把 `\n` 转成 `\r\n`，
于是**每一次经批准的改动都被报成漂移** —— 修法本该生效，在 Windows 上
却恰好和 bug 的表现一样。

这和 v0.7.77 抓到的那次是**同一族**：**拿两个不同基准的数字做比较，
等于没比较**。修法也一样 —— 改用**磁盘上的字节哈希**去查批准。

### 这条不变量由第 54 项门禁 `seal_takeover` 守着

```bash
mas selftest --only seal_takeover
```

门禁要求：经批准的改动**不能**被报成漂移、**没**批准的改动**必须**报漂移、
撤销过的批准**不**背书、跨文件夹的批准**不**背书、链坏**不**背书、
报告与 JSON **说同一件事**。

门禁**独立实现两遍判定**，并**自证能失败**：把 take-over 故意打回漂移，
门禁必须报红。

## 第二十八条不变量：一次批准被撤回了，这次运行必须自己知道（v0.8.9）

第二十七条不变量管的是**决定算在谁头上**。这一条管的是**这次运行自己知不知道自己错过**。

### 洞在哪里

第二十七条让**账本**能回答「我这几次运行里，哪几次一度批错了」。
但**运行自己**答不了。

`mas/report.py:group_runs()` 一直把决策行**排除在运行之外**：

```python
if str(row.get("role") or "") in DRAFT_DECISION_ROLES:
    # A human decision about a draft is not a run. Folding it
    # into one would invent a run with no closure and no goal,
    # and the report would list it as an unfinished problem.
    continue
```

这个判断是**对的**：人对草稿的决定不是一轮循环，
把它塞进去会凭空造出一个没有目标、没有闭合的运行。

但这个判断在**读**的时候留了个洞。运行摘要数了五条记录、
说了句「已闭环」，对「人把它的批准收回去过」**一个字都没有**。

于是读者打开**唯一出过错的**那次运行，看到的是一次**干干净净的成功**。

实测（v0.8.9 之前的探针）：跑一次真闭环，在它上面 stage→approve→undo 之后，

```text
run_summary 的 keys 里没有任何 draft / undo 相关字段
status: closed     seal_state: holds     seal_ok: True
```

那次运行**完全不知道自己**的一次批准被撤回了。

### 这条不变量说了什么

| 边界 | 含义 |
| --- | --- |
| **不塞进运行** | 决策行仍然不是运行行 —— 运行数不会因为人做了个决定而变多 |
| **挂在旁边** | 决策行按 `run_id` 挂在**提议它的那次运行**上 |
| **读成自己的事实** | 运行摘要多出 `decisions` 与 `taken_back_approvals` |
| **配对不重写** | 沿用 `mas/undos.pair_decisions` 的堆栈配对，不自己发明一套 |
| **没有线程的不算** | 没有 `run_id` 的老决策行**不属于任何运行**，不被摊到每一次运行头上 |
| **四面一致** | 报告表、运行详情、命令行、MCP 说同一件事 |

### 为什么是「挂在旁边」而不是「塞进去」

塞进去会造出**没有目标的运行**：一次批准不是一轮循环，
它没有起点、没有闭环、没有交付物。报告会把这样的东西
列成「一次没做完的尝试」，让读者去 `mas resume` 它 ——
而那里根本没有活儿可续。

挂在旁边就干净了：分组语义一点没变（决策仍然不是运行），
但**读**的时候，运行能把它自己的决定读出来。

### 现在能问的问题

```bash
mas report                    # 运行表多一列「撤销的批准」
mas report --run-id R-1       # 那次运行的详情里直接说：人撤回了什么
```

运行详情里长这样：

```text
## 运行 `R-8d02b0ef86`
- ⏪ 人工决定：这次运行有 **1 次，退回 1 行** 的批准被人撤回了
  ——那次批准是错的，机器自己不会知道，是人撤回来的。
  - 涉及草稿：`D-6178cb31`
  - 撤回了 `note.txt` 的改动
```

MCP 面也一样：

```json
{"tool": "mas_report", "arguments": {"as_markdown": false}}
// -> runs[].taken_back_approvals
{"tool": "mas_replay", "arguments": {}}
// -> runs[].taken_back_approvals
```

### 这条不变量由第 50 项门禁 `a_run_knows_its_approval` 守着

```bash
mas selftest --only a_run_knows_its_approval
```

门禁**独立实现两遍判定**（`_verdicts` 与 `_verdicts_independent`），
并**自证能失败**：把 `group_runs()` 的**接线**故意打坏
（不再把决策挂在运行上），门禁必须发现运行已经不知道自己的批准被撤回过。

打断的是**接线**，不是共享函数 —— 共享函数坏了会让所有面**以同样的方式**坏，
于是各面仍然一致，门禁什么也看不见。

用例里放了**两次真实的闭环运行**，只有一次出过错：
只放一条的话，一个「永远返回全部」的过滤器看起来和真正生效的过滤器一模一样。

## 第二十七条不变量：一次批准是错的，这条线程得能查出来（v0.8.8）

第二十六条不变量管的是**改动还算不算数**。这一条管的是**决定算在谁头上**。

### 洞在哪里

一张草稿是**提议**。人对它的批准、或把批准收回去，是对这个提议的**回答**。

而这个回答**把问题丢了**。`mas/drafts.py:ledger_row_for()` 把每一行决策的
`run_id` 和 `task_id` **写死成空字符串**：

```python
row = {
    "role": str(entry.get("event") or "event"),
    "run_id": "",      # <- 丢掉
    "task_id": "",     # <- 丢掉
    ...
}
```

于是账本里那行只说了「有人批了 D-abc」，**别的什么都没说**。
提议这个改动的线程**不是没记，是被扔了**。

所以每个人真正会问的那句话，**根本问不出来**：

> 我这几次运行里，哪几次一度批错了？

报告的草稿表本来就有一列「提议运行」，但它对**每一行**都打印 `-` ——
因为账本里根本没有东西可打印。

### 这条不变量说了什么

| 边界 | 含义 |
| --- | --- |
| **提议时就要记住** | 草稿在**被提出的那一刻**就记下是哪一次运行、哪一个任务提的 |
| **决定继承线程** | 决策行把这条线程从草稿上拷下来，不重新猜 |
| **撤销也继承** | 收回批准同样挂在同一条线程上 |
| **两边对得上** | 线程进了交叉校验字段，单边篡改会被抓到 |
| **按运行能问** | 命令行和 MCP 都能只问某一次运行 |

### 线程记在哪里

三处，**一份真相**：

1. **草稿自己**（`mas/drafts.py:stage_draft`）—— 提议那一刻写下的
   `run_id` / `task_id`。这是**源头**：即使账本那行丢了，草稿还知道自己是谁提的。
2. **决策行**（`record_decision` → `ledger_row_for`）—— 从草稿上读下来，
   写进审计链，再由 `ledger_row_for` 拷进主账本。
3. **撤销记录**（`mas/undos.py:_record`）—— 收回批准时也带着线程。

`mas/drafts_reading.py` 读队列时，**草稿自己记的优先**，账本行回填；
两边说得不一样时，那本身就是一条**要人看一眼的问题**：

> 草稿 D-xxx 的提议运行对不上：草稿自己记的是 R-1，账本记的是 R-2

### 现在能问的问题

```bash

mas report                                # 草稿表的「提议运行」列不再是 -
mas undos --run-id R-1                    # 只看 R-1 的批准与撤销
```

MCP 面也一样：

```json
{"tool": "mas_undos", "arguments": {"workspace": "...", "run_id": "R-1"}}
```

```bash

```

门禁**独立实现两遍判定**（`_verdicts` 与 `_verdicts_independent`），
并**自证能失败**：把**决策行的接线**故意打坏（让它不再拷线程），
门禁必须发现「账本里的决策丢了线程」，以及「链与账本不再一致」。

打断的是**接线**，不是共享函数 —— 共享函数坏了会让所有面**以同样的方式**坏，
于是各面仍然一致，门禁什么也看不见。

## 第二十六条不变量：撤销过的草稿仍然等人批（v0.8.7）

第二十五条不变量管的是**批准被撤销过这件事能不能被看见**。
这一条管的是**撤销之后，这个改动还算不算数**。

### 洞在哪里

一张草稿有四种状态。`pending`（没人决定）、`approved`（改动已经落盘）、
`rejected`（改动作废）—— 这三种一眼就懂。第四种 `undone` 不然。

`undo_draft` 把**基线**写回磁盘，然后把草稿置为 `undone`。
而 `approve_draft` 接受 `undone` 状态的草稿 —— 撤销的全部意义就是：
这个改动还能在人想明白之后**再批一次**。

所以 `undone` 的草稿是一个**活着的、等人批准的改动**。

但有三处只读 `pending`：

```text
覆盖层（机检读的字节）      ->  {}          <- 空！机检去读磁盘的基线
队列读法（等人批的张数）    ->  0           <- 「没有东西在等」
闭环判定（这次运行闭合了吗）->  闭合         <- 改动还在人前面
```

第一处最尖锐：**机检在判旧字节，循环在提新字节**。
覆盖层是空的，所以机检读到的是撤销**刚写回**的基线 —— 那个**循环正要改掉的**
旧版本。于是循环永远无法对自己的提议闭环，而没有一个字说明为什么。

第二处让队列说谎，第三处让**判定页**说谎：一个改了文件、但改动还排在人前面的
运行，被报成「闭合」。

### 这条不变量说了什么

| 边界 | 含义 |
| --- | --- |
| **一份读法** | 「还在等人批吗」只在 `mas.drafts_reading.is_waiting_for_human()` 里判一次 |
| **待批 = 未批 + 撤销过** | `pending` 和 `undone` 都是等人，语义上不是两件事 |
| **机检看提议，不看磁盘** | 覆盖层必须带上撤销后草稿的提议字节 |
| **撤销不是死路** | 撤销过的草稿在报告里也要给出再批准的命令 |
| **代理能直接问** | MCP 面给 `waiting_for_human`，不用自己从 `state` 猜 |

### 唯一的那份读法

* 报告的草稿表与闭环判定（`mas/report.py`）；
* 状态页（`mas/cli.py`）；
* MCP 面的 `mas_drafts` 与 `mas_status`。

一处规则，六处不再漂移。

### 覆盖层为什么必须收 `undone`

因为**撤销之后的磁盘内容不是循环的提议**。撤销把基线写回去了，
而循环提的仍然是那个改动。要让机检判「循环自己的提议」，
机检就得拿到**草稿的字节**（`.data`），而不是磁盘上的基线。

`approved` 的草稿**正确地不在**覆盖层里 —— 它已经落盘了，磁盘**就是**新字节。

（让它不再读 `undone` 草稿），门禁必须发现「机检读到了撤销写回的基线」。

打断的是**接线**，不是共享函数 —— 共享函数坏了会让所有面**以同样的方式**坏，
于是各面仍然一致，门禁什么也看不见。

## 第二十五个不变量：被撤销的批准在每一面都看得见（v0.8.6）

第二十四条不变量管的是**队列**。这一条管的是**人工决定**里最容易
丢掉的那一半事实：**批准被撤销过**。

### 洞在哪里

草稿文件只记**最新状态**。一张草稿被批准、被撤销、又被批准一次之后，
它的 `state` 是 `approved` —— 那次错批只活在**审计链**里。

v0.7.85 让**命令行**学会了读链，但 **MCP 面**还在说旧口径：

```text
mas drafts --json   ->  ever_undone=True, undos=1        <- 命令行面：撤销过
mas_drafts (MCP)    ->  ever_undone=None, undos=None      <- MCP 面：什么都没说
```

**一台机器两个答案** —— 而**代理才是那个要动手的角色**。
用 Claude / GPT / Kimi 通过 MCP 驱动这台机器的代理，问「这张草稿还算数吗」，
读到的 `state` 是 `approved`，永远学不到这次批准被收回过。

同一族里还有两个洞：

* **报告**的草稿表只写「已批准」，看不出这张草稿被撤销过 ——
  读者得跨章节自己去「被撤销的批准」那一节对照；
* **状态页**只数 `pending` / `approved`，**根本没有**「批准被撤销过」这一格，
  于是撤销后再没批过的草稿从所有计数里消失。

### 这条不变量说了什么

| 边界 | 含义 |
| --- | --- |
| **一份读法** | 审计链只在 `mas.undos.draft_histories()` 里读一次 |
| **一张面孔一张嘴** | 命令行、MCP 面、报告、状态页读同一条链，说同一个数 |
| **最新状态不是全部** | `state=approved` 不等于「一次都没错过」 |
| **不能只靠跨章节** | 报告的草稿表自己就写「被撤销 N 次」 |
| **计数要有这一格** | 状态页数得出来，否则它从视野里消失 |

### 唯一的那份读法

`mas/undos.py:draft_histories(roots, draft_ids)` 一次读多个草稿的
**批准次数**、**撤销次数**、**是否曾被撤销**、**累计退回行数**。
缺链不是错误 —— 那只说明这个工作区还没有决定，于是那张草稿没有历史。

**四处都调它**：命令行的 `mas drafts`、MCP 面的 `mas_drafts`
（`list` 与 `show`）、报告的草稿表、状态页。

### 链要读对地方

链在**做决定的那个工作区**里 —— 不是在 artifacts 根下。

草稿清单扫**三处**（artifacts / 配置工作区 / 账本命名的工作区）；
如果状态页**只**从 artifacts 根读链，一张放在**自己的工作区**里的草稿
会被**列出来**，但它的撤销**不被计数** —— 页面展示了这个改动，
却藏起了那次错批。

所以状态页的根目录**从草稿自己身上取**（每张草稿都写着自己的 `workspace`），
跟 `mas.drafts` 的三处扫描是**同一套规则**。一处规则，两处不再漂移。


门禁**独立实现两遍判定**（`_verdicts` 与 `_verdicts_independent`，

## 第二十四个不变量：三个面读同一个队列（v0.8.5）

## 第二十三个不变量：工单队列才是「还在等」的权威（v0.8.4）

前四条不变量把**粒度**说到了每一个表面，但**最常见的看法**还是旧的：
单次运行报告。

```bash

```

### 洞在哪里

这份报告的账本里只有那次**失败**的运行。真正把问题关掉的那次尝试（`R2`）
发生在**后来**、**另一次运行**里，**根本不在这个账本里** —— 于是同一页纸上

```text
尝试总数：1　已闭环：0　仍在等：1　尝试闭环率：0%      <- 头部：还在等
| 把事情做完 | 待处理 |                              <- 概览：还没做
| T1 | 已解决 |                                       <- 工单表：已经做完了
- 人工工单：`T1`（已不需要续跑）                      <- 明细：也不用续了
```

四行三个答案，而且**单次报告的读者无从调和** —— 能定案的证据在他没打开的
那份报告里。

根因是**问错了权威**：「还有没有人拿着这个问题」是问**人工队列**的，队列答了；
判定却去问**账本**，而单次运行的账本里只有那次失败。

### 这条不变量说了什么

| 边界 | 含义 |
| --- | --- |
| **队列才是权威** | 「还在等」问**工单队列**，不是问**账本** |
| **队列带着证据** | 一次尝试关掉问题时，工单上记着 `closed_run_id` |
| **被取代的归入历史** | 单次报告里那次失败是**历史**，并**点名取代它的那次成功尝试** |
| **手工关单不算数** | 人手工关掉的工单没有 `closed_run_id`，那次失败**仍是待办** |
| **没读 ≠ 空** | 调用方没交队列就是没看，没看就不能替工单退休，**保留续跑指引** |
| **不藏起工作** | 朝「已完成」方向撒谎是最坏的方向，所以宁可多算一条待办 |

### 唯一的那份读法

`mas/report.py:queue_closed_by_success()` 从**已解决且带 `closed_run_id`** 的
工单里取出「哪次成功尝试关掉了哪个问题」；
`group_threads(runs, closed_by_ticket)` 用它把线程判成闭合，`closed_by`
记的是**关闭者**，不是这条账本里的某次运行。

**只有一处判「还在等」，也就没有第二处可以漂移。**

## 第十九个不变量：工单不只是一串 ID（v0.8.0）

`mas tickets` 会说清楚一张工单是什么：它在做什么任务、卡在哪一条标准、
循环为什么停下、接着该跑哪条命令。那是**特意**这么做的 —— 一个 ID 加一个
类型是「记录」，不是「交接」。

而 MCP 的 `mas_status` 只给了**工单的 ID**：

```json
"open_tickets": ["T-20261121-104405-7a81"]
```

一个智能体问状态工具「现在需要我做什么」，拿到的是一串把手。它**无从知道**
这些 ID 说的是什么事、卡在哪儿、怎么接着干 —— 除非它再去调第二个工具，
而它未必有第二个工具。

### 洞在哪里

这是本项目从 v0.7.89 起一直在修的**同一个形状**：**能力到了命令行，没到智能体
那一边**。

| 版本 | 能力 | 之前的状态 |
| --- | --- | --- |
| v0.7.96 | 交付物清单 | MCP 看不到 |
| v0.7.97 | 闭合的判定 | 两个界面都没有 |
| v0.7.98 | 闭合的粒度 | 报告和判定互相打架 |
| v0.7.99 | 等待的粒度 | 状态页用旧口径，MCP 干脆不说 |
| v0.8.0 | **工单本身** | **MCP 只给一串 ID** |

### 这条不变量说了什么

| 边界 | 含义 |
| --- | --- |
| **ID 是把手，不是交接** | 工单必须带上「是什么」「卡在哪」「怎么继续」 |
| **两边读同一份** | 命令行和 MCP 读**同一个函数**，不是各写一份 |
| **ID 列表照旧保留** | 其他工具拿的正是这个 ID，不能为了好看改掉它 |
| **理由是数据** | 机器理由和**人话理由**都在，调用方自取 |

### 唯一的那份读法

`mas/ticket_brief.py:ticket_brief()` 读一张工单，吐出：

* `title` / `goal` —— 它在做什么；
* `blocked_on` —— 卡在哪条标准（人话）；
* `reason` / `reason_reading` / `reason_hint` —— 为什么停（原始值 + 人话 + 提示）；
* `next_command` / `handback_command` —— 接着怎么跑（**带放宽的预算**，不撞同一堵墙）；
* `workspace` —— 人在哪改；
* `attempts` / `rounds_total` —— 这个问题烧了多少。

命令行和 MCP 都读它。**不再各留一份读法，也就没有第二处可以漂移。**

### 这条不变量由第 41 项门禁 `ticket_brief` 守着

```bash
mas selftest --only ticket_brief
```

门禁要求：MCP 状态工具**带着工单**而不只是 ID；一份摘要**说清卡在哪和怎么继续**；
命令行和 MCP **用同一套话**描述同一张工单；**ID 列表还在**（别的工具靠它）。

门禁**独立实现两遍判定**（`_brief_verdicts` 与 `_brief_verdicts_independent`，
后者完全从**工单原始数据**手算），并**自证能失败**：把摘要**故意打坏**成
「只给 ID」，门禁必须发现智能体又读不懂工单了。

## 第十八个不变量：还在等的是「问题」不是「尝试」（v0.7.99）

v0.7.98 把闭合判定的粒度改成了「问题」。但**判定是唯一一个用新口径的地方**。

### 洞在哪里

`mas status` —— 初学者打开的第一页，也是唯一回答「这台机器现在什么状况」的
那一页 —— 还在数**每一次失败尝试**。于是同一台机器同时说出：

```
账本：尝试 2 次  已闭环 1  未闭合 1
待解决问题：0 个（共 1 个问题）
闭环判定：闭合：没有留下任何待办。
```

三行，两种粒度，屏幕上**没有任何一行说明哪个是哪个**。读者只能猜
「还没等我做的是哪个数」，而答案取决于他先读哪一行。**一台机器，两个答案。**

**同一族的第二层**：MCP 的 `mas_status` 只报 `open_tickets`，**完全不说闭合情况**。
一个智能体问「这活儿干完了吗」—— 问状态工具的第一个问题 —— 从最像能回答它的
地方，得到的是沉默。

### 这条不变量说了什么

| 边界 | 含义 |
| --- | --- |
| **等待是问题口径** | 「还在等」数的是**仍在开放问题里的失败尝试**，不是全部失败 |
| **历史照数不丢** | 被取代的失败仍然计数，并**明说**被取代了几次 |
| **三处表面一个数** | 状态页、报告头部、MCP `mas_status` 报**同一个数** |
| **一份规则** | 三处读**同一个函数**，不是各抄一份 |

### 唯一的那份规则

`mas/report.py:closure_grain()` 算粒度，命令行状态页、报告 Markdown 头部、
MCP `mas_status` 全部读它。**不再各留一份规则，也就没有第二处可以漂移。**

它给出的两个关键数：

| 数 | 是什么 | 例子（失败→成功） |
| --- | --- | --- |
| `attempts_open` | **仍在等**的失败尝试。待办。 | 0 |
| `attempts_superseded` | 已被后来成功尝试取代的失败。历史。 | 1 |

### 这是同一族的第十个洞

前九个的形状是「能力在账本里，主视图不读它」「能力在一个界面里，另一个界面
看不见」「判定规则只存在于人的脑子里」「判定数错了粒度，于是报告自己跟自己
打架」。这一次的形状是：**判定改对了，但只有判定改了；主视图还在用旧口径，
而 MCP 那条路干脆没有闭合这回事。**

| 版本 | 能力 | 之前的状态 |
| --- | --- | --- |
| v0.7.96 | 交付物清单 | MCP 看不到 |
| v0.7.97 | 闭合的判定 | 两个界面都没有 |
| v0.7.98 | 闭合的粒度 | 报告和判定互相打架 |
| v0.7.99 | **等待的粒度** | **状态页用旧口径，MCP 干脆不说** |

### 这条不变量由第 40 项门禁 `status_grain` 守着

```bash
mas selftest --only status_grain
```

门禁要求：状态页的「仍在等」和判定的 `not_closed_open` **数同一个东西**、
状态页把「还在等」和「历史」**分开说**、报告头部**每个数都带粒度**、
MCP `mas_status` **报闭合且粒度相同**、三处表面读**同一个函数**。

门禁**独立实现两遍判定**（`_grain_verdicts` 与 `_grain_verdicts_independent`，
后者完全手算「最后一次尝试决定问题」这条规则），并**自证能失败**：把状态页
**故意打坏**成「每次失败都算待办」（旧口径），门禁必须发现「失败后被成功取代」
的问题又被状态页攥在手里。

## 第五个不变量：并行选优必须是确定的（v0.7.64）

当多个 worker 同时产出候选时，引擎要挑一个交出去。这个「挑」一旦掺进
**赛跑的偶然性**，闭环就漏了：

- 候选池按**完成顺序**回填结果 → 谁先跑完谁赢；
- 平局反向打破 → 同一个任务两次跑出两个交付物；
- 排名把**正文长度**排在机检之前 → 更长但一条标准都没过的稿子赢。

这三种情况运行**照样报成功**——状态是 `closed`，账本也是齐的，只有
交付物悄悄换了。**一个会悄悄换答案的闭环，是不能复盘的闭环。**

所以引擎的排序是死的：`（通过的机检数，正文长度，最小序号）`。同分时取
序号更小的那个，候选池的结果按**投进去的序号**回填，跟谁先跑完无关。

这条不变量由第 6 项门禁 `parallel_pick` 守着（`mas selftest`）。门禁把
赛次**排好**而不是靠运气：用事件链把三个候选的完成顺序钉成逆序，
再让两个候选的机检数和长度完全相同（只能靠序号分胜负）、第三个更长但
一条机检都过不了。任何一处排序被改动，门禁当场变红。

```bash
mas selftest --only parallel_pick
```

## 第六个不变量：没闭合的运行必须留下人能接手的东西（v0.7.65）

闭环跑不出来的时候，它不甩手，它**升级**：开一张票据，等人来接。这个承诺
有三半：

1. 升级，而不是空转 —— 引擎确实这么做了；
2. 开票据，而不是只写一句「失败」 —— 引擎确实这么做了；
3. **票据带够让人接回来的上下文** —— 这一半从来没人守。

第 3 半看着像细节，其实是闭环的最后一环。一张只写了「停滞了」的票据，
人接回来之后拿到的是**一个没有验收标准的循环**：谁说了算？评审。
于是循环照样能闭合、照样报成功 —— 只是它已经不是用户要的那个循环了。
**一个接不回来的闭环，升级就只是把失败换了个地方存。**

所以票据必须带齐：

| 字段 | 人拿它干什么 |
| --- | --- |
| `goal` / `title` | 知道自己在接什么问题 |
| `criteria` | **带机检的**验收标准 —— 这是最要紧的一条 |
| `last_artifact` | 看到最后一版长什么样 |
| `issues` / `reason` | 知道卡在哪、为什么停 |
| `history` / `runs` / `stagnation` | 知道已经烧了几轮、值不值得接着烧 |
| `status` | 知道这次是升级、预算耗尽还是出错 |

`criteria` 之所以最要紧，是因为 **`engine.resume()` 用的就是票据里的
`goal` 和 `criteria`**。标准在票据上丢了或者只剩散文，接回来的循环就没有
标准了 —— 闭环在这一刻静悄悄降级。

这条不变量由第 7 项门禁 `handover_ticket` 守着（`mas selftest`）。门禁的
办法很直接：**把票据用起来**。它让运行升级、开出票据，然后拿票据里的
标准喂回 `engine.resume()`，要求循环真的闭合。这个检查里的 verifier
**永远答 fail**，所以闭环只能靠票据带回来的**机检** —— 模型糊弄不过去，
票据丢了标准就接不回来。票据和账本还得互相指得到对方，否则人找不到问题。

顺带一提：这道门禁在第一次跑的时候当场抓到一个真 bug —— 票据的字段在两条
升级路径上不一致（停滞升级少了 `status`）。现在两条路径共用一个 payload
构造器，**票据只有一个形状**。

```bash
mas selftest --only handover_ticket
```

## 接手：看得见成果，也要换一份预算

票据带齐了上下文，**接手的运行却用不上那份上下文**。这一节是 v0.7.66
补上的最后一环。

### 四个真缺陷

| 现象 | 根因 | 现在 |
| --- | --- | --- |
| 预算触顶的运行被归到「循环自己闭不上」 | token 分支只设了 `decision`，没设状态，被升级分支盖掉 | 预算触顶就是 `budget_exhausted` |
| 接手的运行看不见上一轮的交付物 | 续跑把尝试计数重置成 1、问题清单清空 | 上一轮的交付物交给接手的 worker，并要求在它基础上改 |
| 预算触顶的票据，续跑立刻再次触顶 | `resume()` 完全复用本机配置的预算 | 三条上限按这一轮单独给，且不漏进下一轮 |
| 屏幕上那句「接着干」是死路 | 打印的命令继承了同样的上限 | 续跑命令带上更宽的那一条上限 |

「预算触顶」和「循环闭不上」需要**完全不同**的反应：前者要加预算，后者要
换计划。混在一个队列里，人就会一直查错方向。

### 预算可以按这一轮给

```bash
mas resume T-20261116-064911-7ab1 \
  --max-iterations 8 --deadline-sec 60 --max-tokens 20000 \
  --note "你的意见"
```

这三个旗标**只影响这一轮**，不改本机配置，也不会漏进同一引擎的下一轮。

屏幕上的续跑命令会**自己带上放宽后的上限**（外加一个下限，保证宽出来的
预算真的能干活，而不是把同一堵墙放大一点再撞一次）。旗标名和命令行一致：
`--max-tokens`，不是 `--max_tokens` —— 屏幕上的命令必须能粘贴就能跑。

### 这条不变量由第 8 项门禁 `takeover_handover` 守着

```bash
mas selftest --only takeover_handover
```

门禁把四种停法（轮数 / token / 墙钟 / 后端报错）各跑一遍，要求：

* 每种停法都留下一张说清原因的票据；
* 票据记着这一轮跑在什么预算下；
* 续跑命令带着更宽的预算；
* **接手的 worker 真的看得见上一轮的交付物**；
* **用新预算接手后循环真的闭合**，而且是靠票据带回来的**机检**闭合的。

这道门禁在第一次跑的时候当场抓到两个真 bug：屏幕上的续跑命令旗标名写错
（粘贴就报错），以及放宽逻辑在退化预算下会让续跑再次原地撞墙。

## 人写的交付物，也要走同一道门（v0.7.67）

工单队列以前只有**一个**答案：「续跑，让机器再试一次」。

但循环升级的真实场景往往是反过来的：**人已经把答案写好了**。
模型反复产出不合格的产物，人改好了它 —— 然后系统没有地方放这份东西，
于是那份工作被扔掉，让机器从头再推导一遍，通常还更差。

「接手的运行看得见上一轮的成果」（v0.7.66）解决的是**机器接着干**。
v0.7.67 补上的是**人接着干**：

```bash
mas handback T-20261116-075440-8aae --file 我的交付物.md
```

### 三条性质，让它是一个闭环而不是一个橡皮图章

1. **同一套标准做判定。** 验收标准是从工单上取回来的 —— **就是这件事
   当初写下的那套**，不是重新解释一遍。带机检的标准由机检说了算，
   **评审员不能推翻它**（和正常运行时一模一样）。
2. **不合格的接回不闭合。** 失败项写回票上，工单**留在人工队列里**。
   一次被拒的接回是第二次尝试，不是一次结单。
3. **评审挂了不毁掉人写好的东西。** 机检在调用评审**之前**就已经判完了。
   后端这时挂掉，只会把「评审失败」如实记下来 —— 一份人工写好的交付物
   不会凭空消失。

### 为什么第 3 条是被抓出来的，不是想出来的

第一版的捕获范围比主循环窄：只接住了 `ProviderError`。
探针里让 provider 抛一个普通 `RuntimeError`，结果**手写的交付物直接
连同整个命令一起崩了** —— 而这条路径存在的全部意义，就是**保护人已经
写好的东西**。现在它和主循环一样宽。

### 一句话记住

> 升级不是失败，是**换一个人接手**。
> 接手的人可能是机器（`mas resume`），也可能是你（`mas handback`）——
> **两条路走的是同一道门。**

### 这条不变量由第 9 项门禁 `handback_closes` 守着

```bash
mas selftest --only handback_closes
```

门禁要求：

* 合格的人工交付物**真的闭合**，而且是靠票据带回来的**机检**闭合的；
* 通过的交付物**落到磁盘上**，票据归档成 `handback`；
* 不合格的交付物**不闭合**，失败项留在票上，工单**还在队列里**；
* **评审挂了**，机检已经通过的那份交付物**照样闭合**。

## 报告要看得见「人写的那一步」（v0.7.68）

v0.7.67 让人写的交付物能把环闭闭上。但那份成果在报告里
是**看不见的** —— 报告只认机器跑出来的记录，人交回的东西
在账本里留了一行，却读不出结论。

这一版把这条缝补上。而且是**当场抓到两个真 bug** 才开始的。

### 两个被量出来的缺陷

**缺陷一：环闭了，报告说没闭。**

探针里让人工交回一份合格的交付物，然后去读报告，结果是：

```
closed=False  closure_rate=0.0  problems_open=1
```

根因有两个：

1. 人工交回的账本条目**缺** `closed` / `goal` / `title` /
   `decision` / `files` 等字段，报告根本读不到结论；
2. **分数挂在 `handback` 行上，报告却只读 `closure` 行**。

现在两边都补上，并且报告在**没有机器 closure 记录时**
会回退去读 handback 的分数。

**缺陷二：失败过一次，就永远待处理。**

旧的线程闭合规则是：

```python
closed = all(m.get("closed") for m in members)   # —— 旧的，错的
```

意思是「线程里每一次运行都闭合了，线程才闭合」。
但环闭的实际语义是**最后一次尝试闭合了，就算闭合** ——
人写完、或者后面跑成了，就不应该被永远挂在「待处理」里。

现在线程记录里多了两个字段：`closed_by`（是哪一次运行闭合的）
与 `handback`（是不是人工交回闭的）。

### 报告里新增的「来源」列

问题概览与运行概览两张表都多了一列：

| 来源 | 含义 |
| --- | --- |
| `🤝 人工完成` | 这个问题是人写的交付物关上的 |
| `🤖 机器闭环` | 这个问题是机器自己跑闭合的 |

人工交回的运行还会带一个单独的验收小节（「人工交付物的验收判定：」），
逐条列出通过/未通过，并附上**人的意见**。

### 词汇分开了

机器闭合记 `close`，人工交回记 `handback` —— 两者在账本、报告、
replay 里是**不同的词**。你不再需要从推断里面猜「这次是谁关的」。

### 一句话记住

> 闭环不只有一种形态。
> **机器闭合是一种，人工交回也是一种** —— 而报告必须把两者都说清楚。

### 这条不变量由第 10 项门禁 `handback_report` 守着

```bash
mas selftest --only handback_report
```

门禁要求：

* 人工交回的闭合在报告里是**已解决**的问题，而不是待处理；
* 报告里带着**验收结果**、**人的意见**和**来源**；
* `mas replay` 也标出人工的那一步；
* **被拒绝的交付物不能消失** —— 失败不许从报告里消失。

### 为什么要加第 10 项门禁（这是反证查出来的）

第 9 项门禁 `handback_closes` 看的是**引擎**：人写的交付物能不能按同一套标准闭合。
但**没有任何门禁看报告层**。

所以我们做了**反证**（mutation testing）：拿报告层的六个行为分别破掉，
再看有没有门禁会报败：

| 变异 | 现在被捕获吗 |
| --- | --- |
| 丢掉 handback 的 `closed` 标志 | 是 |
| 决策词从 `handback` 改成 `close` | 是 |
| 报告不再读 handback 的分数 | 是 |
| 线程闭合回到「所有成员都闭合才算」 | 是 |
| 报告忘掉是哪一次运行闭的 | 是 |
| 来源恒说机器 | 是 |

第一次做这个实验时，**六个变异一个都没被捕获** —— 第 9 项门禁一个都拿住。
这就是新门禁的动机：**门禁不仅要证明引擎对，还要证明读者看到的是对的**。

## 人这条路：文件夹交回

前面讲的都是**机器**怎么闭合。但真实世界里最常见的情况是**人已经把答案写好了**。

v0.7.67 的文本交回接的是**一段文字**。而这个循环真正跑的任务写的是**文件**，
验收标准也是**读磁盘的文件机检**。人改这样的任务，做的事是**打开文件改**；
旧的文本交回却要求人把文件内容**粘进命令行**。

这是**第二份工作**，而复制的这一份正好是容易出错的那一份：
**忘了一行，交回就被拒绝** —— 而拒绝的原因与答案本身无关。

### 交付单位是文件夹

```bash
mas tickets
# 在这里改：C:\Users\me\mas-workspace\H-20261116-130330
# 改完交回：mas handback T-20261116-130330-d623 --workspace "C:\Users\me\mas-workspace\H-20261116-130330"

mas handback T-20261116-130330-d623 --workspace "C:\Users\me\mas-workspace\H-20261116-130330"
```

人在**原地方**改文件，交回的是**那个文件夹**。交付物由文件自动生成
（文件清单 + 小文件的正文），**不用手工粘贴**。

### 草稿语义：判定前不写盘

和文档编辑器一个规矩：

1. 文件夹按**现在的样子**被读取（人的改动已经在里面了）；
2. 它按**票据上当初写下的那套标准**判定，机检读到的是**overlay**
   （盘上现在的字节），**什么都不写**；
3. **只有通过了**的交付物才被写回 —— 而且落在**人改过的那个文件夹里**，
   不是第二个文件夹。

**被拒的交回，磁盘原样不动，也不写交付物。**
人改的工作是这个人的，不该被一次失败的验收丢掉。

### 这条不变量由第 11 项门禁 `folder_handoff` 守着

```bash
mas selftest --only folder_handoff
```

门禁要求：

* 文件机检读到的是**人改过的内容**，不是循环留下的旧内容；
* 文本机检看得到**文件的正文**，交付物是从工作生成的，不是手打的；
* **被拒时磁盘字节不变**，且**不写交付物**；
* 接受时交付物落在**同一个文件夹**，offer 包含**全部文件**；
* 票据**写着那个文件夹**，人不用自己去找。

### 为什么要加第 11 项门禁（这是反证查出来的）

第 9 项门禁看**引擎**，第 10 项门禁看**报告**，**没有任何门禁看人这条路**。

所以我们做了**反证**：拿文件夹交回的六个行为分别破掉，再看有没有门禁会报败：

| 变异 | 现在被捕获吗 |
| --- | --- |
| 机检去读另一个文件夹 | 是 |
| 交付物丢掉文件正文 | 是 |
| 被拒的交回也写交付物 | 是 |
| offer 只取第一个文件 | 是 |
| 交付物落到第二个文件夹 | 是 |
| 票据忘记工作区 | 是 |

第一次做这个实验时，**六个变异一个都没被捕获** —— 前面十项门禁一项都拿住。
这就是新门禁的动机：**人这条路也是一条路，它也得被守住**。

## 交付物本身也要看得见：内容级机检（v0.7.70）

前面讲的所有文件级机检，搜的都是**文件的字节**。

这在「文件里有一行这句话」上是够用的。但对**每一种正文不是明文的格式**，
它是**瞎的**：

* PDF 把文字放在**压缩流**里 —— 文件的字节里根本没有那些字；
* `.docx` / `.xlsx` / `.pptx` 本身**就是 zip 包** —— 文字在包里的成员里；
* 图片里**没有文字**，但它有**格式**、有**尺寸**、有**文件头**。

于是**交付物是 PDF 的任务，机检根本判不了**。
标准落回模型手里，模型说一句「looks fine」，
一条**没人查过的标准**就被关上了 —— 这是**假闭合**，比不闭合更糟。

### 六个新的内容级机检

| type | 含义 |
| --- | --- |
| `content_contains` | 文件**内容**含给定字符串 |
| `content_not_contains` | 文件**内容**不含给定字符串 |
| `content_regex` | 文件**内容**命中正则 |
| `content_lines_min` | 内容**非空行**数下限 |
| `content_min_chars` | 内容**字符数**下限 |
| `content_format_is` | 文件**格式**等于给定格式 |

底层是 `mas/content.py`，**只用标准库**，**不执行文件里的任何东西**：

* `detect_format(path)` —— **magic bytes 优先，扩展名兜底**。
  扩展名会撒谎，`.txt` 里装的是 PDF，那它就是 PDF。
* `extract_text(path)` —— 取出读得出来的文字：PDF 解 FlateDecode 流并抽
  `(...) Tj/TJ` 字符串；Office 文档解 zip 成员并**剥掉 XML 标记**；
  zip 读成员；图片没有文字但**读得开**。
* `describe_file(path)` —— 一张事实表：格式、大小，以及格式自己的事实
  （PDF 的**页数**、Office 的**成员数**、PNG/GIF/BMP 的**像素宽高**）。

### 最要紧的一条：读不出内容 = 不通过

按第一层的纪律，「判不了」应该是 `unjudged`。**这一层不一样。**

`unjudged` 会**回到模型手里**。而模型对「这个文件看起来没问题」这句话
是**不会拒绝**的 —— 于是那条标准被**一句话**关上了。

所以内容级机检读不出内容时判 **`pass: false`**。
标准留在那儿，**等人来修**。

### 草稿语义同样适用

要写的新文件，机检按**将要写进去的那份字节**判（overlay）。
候选还没落盘，判据却已经在了。

### 这条不变量由第 12 项门禁 `content_check` 守着

```bash
mas selftest --only content_check
```

门禁要求：

* 内容机检**读得到**压缩 PDF 里的字，而**字节级机检读不到**（这一条证明测试有意义）；
* 内容机检**读得到** Word 文档里的字，而且读到的是**文字不是标记**；
* 格式检查**说得出**格式，**判得出**错；
* **读不出内容的文件判不通过**，不是「未判定」；
* **要写的新文件按将要写进去的内容判**。

而且门禁**每轮故意把内容路径打断一次**，然后确认自己**注意到了** ——
**不会失败的门禁不算门禁**。

### 为什么要加第 12 项门禁（这是反证查出来的）

第 9 项看**引擎**，第 10 项看**报告**，第 11 项看**人这条路**，
**没有任何门禁看交付物本身的内容**。

所以我们做了**反证**：拿内容路径的九个行为分别破掉，再看有没有门禁会报败：

| 变异 | 现在被捕获吗 |
| --- | --- |
| PDF 流不解压 | 是 |
| Office 文档掉进 zip 分支 | 是 |
| XML 标记不剥 | 是 |
| 内容检查去读字节而不是内容 | 是 |
| 读不出内容判成「未判定」 | 是 |
| 格式检查恒过 | 是 |
| overlay 被忽略 | 是 |
| 门禁自己不再看内容 | 是 |
| 门禁丢了一条观察 | 是 |

第一次做这个实验时，**九个变异里有三个没被捕获** ——
其中两个是**门禁自己的缝**（它可以在自己不看内容的时候照样报「全过」）。
现在的门禁把「记录观察」和「下判断」**分开**，观察少一条就会报出来。

## 循环也要能写出二进制交付物（v0.7.70）

上一节让机检**读得进** PDF。可是**读得进**只解决了一半：
**得先有一个 PDF 存在**。

而写文件协议（v0.7.15）只能带**文字**。worker 的输出是一个字符串，
引擎把它写成 UTF-8。于是**交付物是 PDF 的任务**，
worker 无论多努力都**产不出** PDF —— 验收标准判不了，循环闭不上，
而原因跟答案本身毫无关系。

### 写块现在能带 `encoding`

```
<<<MAS:FILE path="out/report.pdf" encoding="base64">>>
JVBERi0xLjQK...
<<<MAS:END FILE>>>
```

引擎把块里的内容**解码成真正的二进制**再落盘。
**不写 `encoding` 的块仍旧按文本写** —— 旧协议一点没变。

### 这条不变量由第 13 项门禁 `binary_write` 守着

```bash
mas selftest --only binary_write
```

门禁要求：

* base64 写块**落盘是真字节**，不是它的 base64 文本；
* **写出去的字节就是机检读到的字节** —— 写路径和读路径必须一致；
* **不认识的编码被拒**，**坏掉的 base64 被拒**，而且**不留半截文件**；
* 不写编码的块**仍旧按文本写**；
* **内容级标准形成写文件义务** —— 不然 worker 只会「 口头说」那个文件；
* 引擎规划的是**二进制字节**，不是旁边的文字。

而且门禁**每轮故意把写路径打断一次**，然后确认自己**注意到了**；
路径**崩了**也算「注意到了」 —— 一个只会崩的门禁比一个会报的门禁更没用。

### 为什么要加第 13 项门禁（这也是反证查出来的）

第 12 项门禁看**读**，**没有任何门禁看「写」**。

所以我们做了**反证**：拿写路径的七个行为分别破掉，再看有没有门禁会报败：

| 变异 | 现在被捕获吗 |
| --- | --- |
| overlay 装的是字节的**个数**不是字节 | 是 |
| 编码被忽略 | 是 |
| base64 被解成文本 | 是 |
| 不认识的编码被接受 | 是 |
| 内容机检不算写义务 | 是 |
| 坏 base64 被悄悄吞掉 | 是 |
| 计划里装的是编码文本 | 是 |

第一次做这个实验时，**有一个变异没被捕获** ——
而且它抓到的**不是假想的 bug，是真的**：

**overlay 装的是字节的个数，不是字节。**
并行选优要给每个候选打分，overlay 取的是 `planned["bytes"]`，
那是**长度**。于是每一份文件机检读到的都是**一个数字**而不是那个文件 ——
**会写出正确 PDF 的候选，输给了会什么都不写的候选**。

真实字节在 `planned["data"]` 里。现在 overlay 由
`LoopEngine._planned_overlay()` **统一构造**，只装 bytes，
装不进 bytes 的一律跳过。

### 一并修掉的两个小 bug

* **base64 静默吞掉垃圾** —— 宽松解码会把不在字母表里的字符全丢掉，
  于是一段纯胡话被解成**一个空文件**、一声不吭。现在**严格解码**。
* **不认识的编码被默默丢掉** —— `encoding="rot13"` 的块被拒绝了，
  但**错误信息没往外传**：没有文件、没有报错、账本里也没有线索。
  现在理由会一起交出去。

## 第三十四条不变量：人工接手，在每一个面上都看得见（v0.11.3）

第三十三条不变量管的是**指控的分寸** —— 人批准过的改动不叫漂移。
这一条管的是**这个分寸有没有传到你眼前的那一面**。

### 洞在哪里

v0.11.2 给封存加了第三种状态：`taken-over`（人工接手）。

封存复核有五个面：**报告**、`mas seal`、**状态页**、**回放**、**MCP**。
v0.11.2 之后，只有报告和 `mas seal` 会说「人工接手」。

状态页和回放**一个字都不说** —— 不是说得含糊，是**完全沉默**：
不封存、不漂移、不接手，一个字都没有。

于是同一个事实有了两种读法：

    读报告的人   -> 知道有人接手了这个交付物
    读状态页的人 -> 什么都不知道，只能假设文件从没被动过

而**状态页恰恰是新手第一个打开的面**。回放也一样 ——
它的本职就是回答「运行闭合之后，文件怎么了」，
而它对漂移、接手、封存**全都沉默**。

沉默会被读成「什么都没发生」—— 和事实正好相反。

### 这条不变量说了什么

| 边界 | 含义 |
| --- | --- |
| **读法只写一遍** | `seal_overview()` 算一次，五个面都调它 |
| **五个面都得说** | 报告、状态页、回放、MCP 状态、MCP 回放 |
| **数是一样的** | 一个事实五个面，不是五个事实 |
| **锁没有放宽** | 没批准的改动，在每一面上仍然是漂移 |

### 为什么读法必须只有一处

因为**同一件事被五处各算一遍，就会有五个答案**。

这不是理论担心 —— `replay_trace()` 原来就对同一枚封存**读了两遍盘**
（一次为了 run 块，一次为了 thread）。封存复核是要**读磁盘**的：
文件若在两次读之间变了，同一个闭环就会拿到两个互相矛盾的结论。

现在它**只读一次**。读法也只有一处：

    seal_overview(runs)  ->  { sealed, holds, no_verdict, taken_over, drifted, items }

报告、状态页、回放、MCP 全部从这一份结果里取数。**它们不可能互相矛盾**，
因为它们没有各自的算法。

### 一个门禁设计上的要点

第 55 项门禁**故意打坏的是「一个面」，不是共享的 helper**。

这是有讲究的：打坏共享 helper，五个面会**一起错**，于是它们
互相「一致」，门禁反而**看不见**问题。要让门禁真的能发现，
必须让**一个面**读出不同的东西。

所以它打的是状态页 —— 让状态页看不见「人工接手」这一个状态
（其它状态还在），门禁必须发现「有一个面瞎了」。

## 第三十五条不变量：套件必须收敛，而且截断时必须说（v0.11.4）

第三十四条不变量管的是**结论有没有传到你眼前的那一面**。
这一条管的是更靠底的东西：**结论本身是不是真的被算出来了**。

### 洞在哪里

这一版的起点不是一个功能缺口，是一次实测。

CI 的 Linux 腿跑 **31 分钟**，Windows 腿只要 11–18 分钟。
同样是 120 次迭代，凭什么差这么多？

去数进程就明白了：门禁跑到一半，机器上已经躺着 **14 个
`serve()` 僵尸** —— 每一个都卡在一个**永远不会到来的读**上。

根因是 `mas/selftest.py` 里的 MCP 门禁：它起了 stdio 服务器，
却没有关掉 stdin。stdio 服务器读到输入流结束为止，
管道不关，它就永远不走。

这个泄漏**在写它的机器上是隐形的** —— 子进程比测试活得久，
而测试并不会因此变红。它在**代价最痛的地方**才显形：
CI 每轮迭代漏一个，Ubuntu 3.13 那条腿就跑到 31 分钟。

更糟的是第二件事：**被截断的套件会说自己通过了**。

`--iterations 120` 跑 644 秒，如果给它一个 600 秒的预算，
剩下的 32 项**根本没跑** —— 但结果里写的是 `ok: true`。
读的人只能读成「全部 55 项都过了」。

### 这条不变量说了什么

| 边界 | 含义 |
| --- | --- |
| **套件不留后手** | 跑完之后，机器上不能多出一个它起过的进程 |
| **收摊是门禁的责任** | 服务器必须由**起它的那个门禁**关掉，不是等操作系统回收 |
| **截断必须说** | 预算耗尽时，结果里要列出**没跑到**的是哪几项 |
| **绿不等于跑完** | `ok`（跑过的都过了）和 `complete`（整个跑完了）是两件事 |
| **退出码要能区分** | 0 = 全过，2 = 有失败，3 = 被预算截断 |

### 怎么数进程：一个只能从里面数的问题

这一条的技术难点不在「数进程」，在**数的是谁的孩子**。

一个泄漏的服务器，在它的父进程还活着的时候，是父进程的**直接子进程**。
但父进程一旦退出，操作系统会把它**改挂**到别处去 ——
这时候再从外面按父子关系去数，**数不到了**。

实测就是这个形状：泄漏版跑起来时能看到 2 个后代（套件 + 服务器），
套件一结束，那个服务器就成了孤儿，**事后按树数是 0**。

所以判据只能**从里面问**：

    套件自己数自己的孩子 -> 收摊了是 0，没收摊是 1

这也是为什么门禁要**在同一时刻**取这个数：它是父进程还活着的时候
问的，问的就是它自己有没有留下后手。

### 为什么门禁要能自己失败

一个只会变绿的门禁是装饰。第 56 项门禁 `selftest_converges`
做了一件事：它**复制一份套件，把 MCP 门禁的收摊代码删掉**，
然后用**同一套判据**去审这份坏掉的套件。

    好套件 -> children_left = 0 -> 门禁绿
    坏套件 -> children_left = 1 -> 门禁红

这条红是**真的红**，不是「理论上应该能发现」。它在
`tests/test_selftest_converges_114.py` 里被钉住，
每次都跑。

### 顺带修掉的：套件不再重复自己

这一版把测试套件的重复跑法收敛了。

以前**八个测试模块**各自跑一遍全量门禁，而它们问的其实只是
「一共几项」和「某一类能不能离线跑」。前者用 `--list` 回答
（1.2 秒），后者用 `--only` 回答（只跑那一项）。

另外还有两个测试**真的打到了外网** —— `base_url=""` 会让
provider 去连一个空地址然后等超时。一个模块 120 秒变成 48 秒。

| | 之前 | 现在 |
| --- | --- | --- |
| 八个全量断言模块 | 300+ 秒 | 184 秒 |
| `test_setup_bench.py` | 120+ 秒 | 48 秒 |
| 完整 pytest 套件 | 641 秒 | 524 秒 |
| 门禁残留进程 | 14 个 | **0 个** |

## 第三十六条不变量：看不见就不能说看见了（v0.11.5）

第三十五条不变量要求门禁**报告套件的泄漏**，前提是门禁**看得见**。
这一条补上那个前提。

### 洞在哪里

v0.11.4 的第 56 项门禁在 Linux 与 Windows 上是绿的，**在 macOS 上是红的**。
它给的失败理由是它自己发现的：

    这个平台没法让一个进程看见自己的孩子，门禁无法证明自己不是瞎的

这不是门禁判断错了，是**平台的能力本来就不一样**。
上一版只会两种读法：Linux 的 `/proc`、Windows 的 tool-help 快照。
**macOS 不发布 `/proc`**，所以进程表读出来是「不可用」。

### 修法

macOS 发布**同样的两个事实** —— 进程号、父进程号 —— 通过 `ps`：

    ps -A -o pid= -o ppid=

`=` 让 `ps` 不要表头。带表头的话第一行不是一对数字，解析会把它跳过。

**一个必须处理的坑**：`ps` 自己是计数器的**孩子**。计数器在数的
那一瞬间，`ps` 就是它起的进程 —— 不按 `ps` 自己的 pid 剔掉，
**每次调用都会误报一次泄漏**。

另加 `ps -eo pid=,ppid=` 作退路：第一种写法被拒绝时再问一次，
而不是直接放弃。**一个在它被写出来的平台上瞎掉的计数器，
比没有计数器更糟。**

### 为什么这值得单列一条

这类 bug 有个共同点：**在写它的机器上是隐形的**。

门禁在 Windows 上写、在 Windows 上跑，Windows 有 tool-help，
一切正常。它被推到 macOS 上才第一次说话 —— 说的是
**「我看不见」，而不是「我没有问题」**。

平台看不见时它没有假装看见，而是把「我瞎了」当成一次失败报出来。
**这正是第三十五条要的那件事**：一个看不见的套件，
和一个没有问题的套件，在结果里必须长得不一样。

| 平台 | 进程表怎么读 |
| --- | --- |
| Linux | `/proc/<pid>/stat` —— 每个进程写着父进程号 |
| Windows | tool-help 快照 API —— 通过 `ctypes` 调标准库 |
| macOS / BSD | `ps -A -o pid= -o ppid=` —— 零依赖，剔掉计数自己的助手 |

### 读法只写一遍

`ps` 的输出解析是一个**纯函数**（`_parse_ps_output`），
所以它可以在**每一个平台**上被测 —— 包括那些真正用 `/proc` 的平台。
一个只在写它的地方能用的门禁，是**在发布之夜才会失败的那种门禁**。

## 第三十七条不变量：重新来过的人，必须看得见上一次（v0.11.6）

前三十六条不变量几乎都在管**证据**：判定要钉在字节上，结论漂移要
被说出来，账本被篡改要被发现。这一条管的是**过程**：

> **一个循环第二次尝试时，工人必须看得见第一次尝试交付了什么，
> 也必须看得见复盘角色自己说的话。**

### 洞在哪里

在 v0.11.5 之前，`LoopEngine.run()` 一次运行里的多轮迭代，
**第 2 次的工人看不到自己上一轮交付了什么**。

`state["previous_artifact"]` 只在**恢复运行**那条路径上被设置
（恢复一个没闭合的运行时才走得到）。同一次 `run()` 内部的迭代，
它**一次也没有被设置过**。

更糟的是**复盘角色（reflector）的产出整段丢失**。
引擎在 `engine.py` 里算出了 `reflection`，然后只做了两件事：
写进日志、赋给一个局部变量。它**从来没有被放进下一轮的 state**。

于是第二轮的工人手里只有两样东西：

1. 机检的一句抱怨 —— `c1: missing: ['关键词']`
2. 什么都没有

复盘角色写了「你缺的不是一个关键词，是整段论证」，
这句话**根本没有到工人手里**。而 `engine.py` 里那句注释偏偏写着：

    the plan and the reflection travel to the model on the next call

注释描述的是**应该发生什么**，代码做的是**另一件事**。

还有一个更根本的问题，连复盘角色自己都没躲过：
**复盘角色看不到它要复盘的那份交付物**。
它被要求评价一篇作文，却只收到了「c1: missing: [...]」。

### 修法

三处一起补，缺一不可：

| 位置 | 补什么 |
| --- | --- |
| `mas/engine.py` `_carry_feedback()` | 上一轮的交付物与上一轮的复盘，随 state 一起进入下一轮 |
| `mas/roles.py` `_brief()` | 解析 `state["reflection"]`，渲染成工人和复盘角色都看得见的一段 |
| `mas/roles.py` 复盘角色的 prompt | 渲染「上一轮的交付物」与机检结果，让它评的是**那份东西**，不是一句抱怨 |

关键的三条线，现在真的连上了：

    上一轮的交付物 ──┐
                    ├──> 下一轮的 state ──> 下一轮工人的 prompt
    上一轮的复盘   ──┘

### 反馈不能无限长

上一轮的交付物可能有十万字。全塞进 prompt 是另一种坏。

所以截断**保留尾部**，并显式标出省略了多少字：

    ...（前面 1234 字已省略 / 1234 earlier characters omitted）

保留**尾部**而不是头部，是因为尾部才是刚刚写出来的那部分 ——
问题通常出在最后一段，开头只是背景。

### 这条不变量怎么被证明

第 57 项门禁 `feedback_reaches_worker` 盯着这件事，而且它**必须能被证伪**：

- 它用**两套独立实现**判定同一件事 —— 一套读 prompt 文本，
  一套解析 `<<MAS_STATE>>` 里的 JSON；
- 它**自证失败**：把 `engine._carry_feedback` 换成空实现，
  门禁必须变红。

一个不会红的门禁是装饰。这条门禁**被证明过会红**。

### 为什么值得单列一条

因为它是**闭环最便宜的一处浪费**：工人看不见上一轮，
就只能从头重写；复盘说的话送不到，
就等于每轮都在做**第一次尝试**。

轮次多不等于闭环好。**第二轮比第一轮聪明，才叫迭代**，
否则那只是**用更多的钱买同一份东西**。

## 第三十八条不变量：计划必须到达第一轮工人手里（v0.11.7）

前三十七条不变量管的是**证据**和**反馈**。这一条管的是**更前面
的一件事**：第一轮那一次尝试，到底是不是**照着计划写的**。

> **一个循环的第一个工人，必须看得见计划。**

### 洞在哪里

引擎里有一个规划角色（planner）。它在第一次迭代的**开头**被调用，
花掉一次真实调用，然后它的答案被记进账本。

然后呢？

用探针 provider（记录每一次 prompt）实测同一轮运行内的多次迭代，
测出来是这样：

    call order: ['planner', 'worker', 'verifier', 'reflector', 'worker', ...]
    worker#1  sees PLAN_SUMMARY=False  sees PLAN_STEP=False
       state.plan.summary=None
    worker#4  sees PLAN_SUMMARY=True   sees PLAN_STEP=True

**第一个工人是盲写。**

那个「从零开始写出交付物」的那一次尝试 —— 整个循环里最关键的
那一次 —— **手里没有计划**。计划算出来了、付了钱了、记了账了，
然后送给了**第二轮**的工人。

根因不是缺功能，是**顺序错了**：

* 迭代的 state 是**迭代运行之前**构造的；
* 规划角色是**迭代内部**才被调用的。

所以 state 被构造出来的时候，里面装的是**一个还没跑过的规划角色
的计划** —— 一个空 dict。规划角色的答案进了 `plan_payload`，
**从来没有回填进 state**。

最坏的情况更难看：`max_iterations=1` 时，
规划角色被调用了、钱花了，**答案一个工人也到不了**。

### 修法

规划角色答完之后，立刻把计划写回 state：

    state["plan"] = plan_payload

一行。这一行放在剥离内部字段之后、写账本之前 —— 因为**这一行
本身就是**账本要记的那件事的另一半：账本里有一笔规划的钱，
而读那笔钱所买的东西的工人，就该拿到它。

一次写入覆盖所有下游：worker、verifier、reflector、lead
全都是从 state 里读计划，写一次就够。

### 这条不变量怎么被证明

第 58 项门禁 `plan_reaches_the_first_worker` 盯着这件事：

| 观察项 | 它在问什么 |
| --- | --- |
| `the first attempt sees the plan summary` | 第一个工人看得见计划摘要吗 |
| `the first attempt sees the plan steps` | 第一个工人看得见计划步骤吗 |
| `the plan is in the state, not only in the prose` | 计划是 state 里的**事实**，不只是简报里的一行字 |
| `a single-iteration run still reaches its worker with the plan` | 只跑一轮时，计划还到得了工人吗 |
| `the second attempt still sees the plan` | 修第一轮的时候，没有把第二轮弄丢 |

它用**两套独立实现**判定同一件事：一套读 prompt 文本，
一套解析 state 块里的 JSON；并且**自证失败** ——
把规划角色的答案掐掉，门禁必须变红。

第三项观察值得单独说一句：**计划和简报是两条通道**。
简报对了而 state 是空的，那么 verifier 和 reflector 读到的
仍然是那一个空的 —— 门禁必须去问 state，而不能只问 prompt 文本。

### 为什么值得单列一条

因为这是**整条链上最贵的一处静默浪费**：

* 规划的钱照付；
* 规划的内容照记；
* 规划的内容**照不到第一个工人手里**。

而第一个工人恰恰是**唯一一次真正从零开始写**的那一次。
计划只对第二次以后的尝试有效，等于说：**这个循环最要紧的那一步，
是在没有计划的情况下做的。**

这也提醒了一件事：**账本里有一笔账，不等于那笔钱买到的东西
被用上了。** 闭环的最后一格，往往不是「有没有算」，而是
「算出来的东西有没有到得了要用它的那一步」。

## 第三十九条不变量：主线的决定必须真的被读到（v0.11.8）

前三十八条不变量管的是**证据**和**反馈**。这一条管的是**顾问**：
一个被问了、付了钱、记了账、还印在报告上的意见，
到底有没有真的影响运行。

> **顾问说「交给人工」，循环就必须真的停下来交出去。**

### 洞在哪里

五个角色里有一个主线（lead）。它的角色契约明确要一个决定：

    {"decision": "close|revise|escalate", "reason": str,
     "judged": [{"id": str, "met": bool, "note": str}]}

并且写得很清楚：**「剩余的工作需要人处理时，用 "escalate"」**。
README 里也写着它给 `close` / `revise` / `escalate`。
报告里甚至把 `decision` 印了出来 —— 所以复盘的人能在主线那一行
看到「escalate」两个字。

但引擎**从来没读过它**。`mas/engine.py` 里 `lead.get("decision")`
**零命中** —— 引擎只取顾问答案里的 `judged`。

用探针 provider 实测三种回答：

    === lead says: escalate ===
      status: budget_exhausted  closed: False
      history decisions: ['revise', 'revise', 'revise']
    === lead says: close ===      <- 完全一样
    === lead says: revise ===     <- 完全一样

**三个不同的回答，同一种行为。**

更糟的是第二层：顾问说「escalate」不但没被听，
运行还会**继续烧完剩下的每一轮**，直到撞上迭代上限 ——
顾问请求人工的那一次，让用户多付了**所有剩余轮次的钱**。

同一个分支里还藏着第二个 bug：引擎**自己**因为停滞
（交付物不再变化）而升级之后，主线分支会把 `decision` 重置成
`close` / `revise` —— 于是引擎自己给出的、**有证据支撑**的停止，
被顾问的回答**降级**成了「再来一轮」，
而那正是那个已经卡住的循环。

### 修法：顾问是顾问，不是法官

主线的决定在**一个地方**被读到，规则只有一条：

* `escalate`：**停下循环，把问题交给人**，并带上顾问自己的理由 ——
  但**只在这次运行本来就不拟闭合时**（全都过的运行没什么
  需要人做的）；
* `close` / `revise`：**不推翻引擎自己的判断**。
  机检失败是**事实**，预算是**用户的**；顾问是顾问。
  这条不变量本来就在 README 里写着，这次修复没有削弱它。

引擎自己的停止也**活了下来**：停滞升级不再被主线分支重置回
`revise`。

### 交出去的时候，人要看得见什么

`lead_escalation` 是**第三种停法**，既不是天花板、也不是后端故障：

* 运行状态是 `escalated`，不是 `budget_exhausted`；
* 票据的 `reason` 里写明「主线判断剩余工作需要人」，
  并附上**顾问的原话**；
* 票据新增 `lead_verdict` 字段，带着顾问**结构化的**回答
  （`decision` / `reason` / `judged`）；
* `stopped_by` 是 `lead_escalation`，报告里读作
  「主线交给人工（主线判断剩余工作需要人）」。

一份只说「升级了」而不知道为什么的票据是**便条，不是交接**。

### 这条不变量怎么被证明

第 59 项门禁 `lead_decision_is_honoured` 盯着这件事，7 条观察：

| 观察项 | 它在问什么 |
| --- | --- |
| `a lead that says escalate stops the run early` | 主线说 escalate，运行真的停了吗 |
| `the run does not burn its remaining rounds after the escalation` | 停得**够早**吗，剩余的轮次没被烧掉吧 |
| `the ticket says the advisor asked for a human` | 票据说清楚是顾问要的人吗 |
| `the ticket carries the advisor's own reason` | 票据带着顾问的原话吗 |
| `the ticket carries the advisor's structured answer` | 票据带着顾问结构化的回答吗 |
| `a lead that says close does not close a failed check` | 顾问说 close，能推翻机检吗（**不能**） |
| `the engine's own stagnation stop is not demoted by the advisor` | 引擎自己的停滞升级，会被顾问降级吗（**不会**） |

它用**两套独立实现**判定同一件事：一套读**运行的结果**，
一套读**运行留下的票据** —— 因为票据才是人真正读的那一份。
并且**自证失败** —— 把主线答案里的 `decision` 掀掉，门禁必须变红。

### 为什么值得单列一条

这是一个**闭环里最容易被写出来的假承诺**：

* 角色契约里写着「escalate」；
* README 里承诺它会交出去；
* 报告里**印着**顾问的决定；
* 而引擎**一行都没读**。

凡是**能被打印出来**却**不影响行为**的东西，都是闭环的漏洞：
它让复盘的人以为某件事发生过。判据其实一直在项目里写着 ——
「**能证明某件事的能力，却没有被主视图消费，就等于没有**」，
这条不变量管的是同一件事的另一头：能力存在，但**没人读**。

顾问的价值恰好在**停止**：它知道这一轮该由人接手。
一个被问了、付了钱、记了账、印在报告上，却**什么都没发生**的顾问，
比没有顾问更糟 —— 因为它让循环**继续烧钱**，同时让人以为
已经有人接手了。

## 一个反直觉的点

**给模型更多轮次不一定提高成功率。** 如果产物在连续几轮里一模一样，那多给 10 轮只是多烧 10 轮的钱。
所以停滞检测不是「优化项」，而是**省钱项**：它把「模型卡在同一个错误上」变成一个人类立刻能看到的信号。

这也是为什么本项目把 `stagnation_limit` 默认设为 3 而不是更大。

## 怎么度量你的循环

跑完之后看账本：

```bash
mas ledger --tail 50
```

关注三个数：

- **闭合轮数**：从第一次执行到通过用了几轮（轮数越少，标准写得越清楚）；
- **判定来源分布**：`source` 里 `rule` 占比越高，结论越可复现；
- **是否升级过**：`escalated` 说明标准或目标还需要人介入，这是信息不是失败。

## 第四十条不变量：主线的判断必须变成下一轮要改什么（v0.11.9）

前三十九条不变量管的是**证据**和**反馈**。这一条管的是**顾问的
判定落到哪儿**。

### 顾问写的判定，和顾问写的理由，是两件事

上一版让引擎**读到了**主线的决定：主线说 `escalate`，循环就真的
停下来交出去。但顾问**自己写下的理由** —— 那一句话说明
「到底缺什么」—— 仍然只停在账本里。

它漏掉的时候，闭环里是这样的：

    === the advisor judged c1 as NOT met ===
      result.issues : ['c1: unjudged: 评审没有给出该标准的判定']
      -> the issue says 'unjudged' even though the advisor judged it: True
      -> the advisor's own note is nowhere in the issues: True

    === worker #2 (the one after the advisor spoke) ===
      sees lead NOTE     : False
      sees lead REASON   : False
      sees 'unjudged'    : True

三件事同时错了，而且它们其实是**一件事**：

1. **`issues` 在主线发言之前就定稿了。** 它本来是「机检 + 评审
   都没给出判定」的清单；主线补上判定之后，这张清单**不重算**。
   于是工人收到的是一句**关于答案缺失**的指控，而这条标准
   恰恰已经有了判定 —— 只是是主线给的。工人被要求去补一个
   它根本补不上的东西。
2. **主线自己的话没走过去。** 下一轮带走的是交付物和复盘的反思，
   主线那段话不在里面。
3. **复盘也不知道主线说了什么。** 而复盘恰恰是那个负责说
   「该怎么改」的角色。

### 顺序是根因

主线被咨询得太晚 —— 在复盘**之后**；而 `issues` 在两者**之前**
就算好了。所以主线的判断**永远追不上**那张清单。

这一版把主线咨询**前移到复盘之前**，让 `issues` 从**主线发言之后**
的 scores 重算，并且让主线的 `decision` / `reason` / `judged`
经由 `lead_advice` **随下一轮和复盘一起走**。

### 没有被改变的：顾问仍然不是法官

这是必须一起说清楚的部分。README 里写着「主线是顾问，不是法官」
「机检失败是事实」「引擎保留最终否决权」—— 这条契约
**没有**被这一版削弱：

* 主线说 `close`，**不能**盖掉未通过的机检；
* 主线只能**叫停**循环，不能**宣布通过**；
* 唯一它能决定的是「没人能判的标准，它来判」。

新门禁把这两条当成**回归**盯着 —— 修好一条路，不许踩坏另一条。

### 这条不变量怎么被证明

第 60 项门禁 `lead_reaches_the_next_worker` 盯着这件事，8 条观察：

| 观察项 | 它在问什么 |
| --- | --- |
| `the issues carry the advisor's own note` | 清单里带的是主线自己的说明吗 |
| `the issues no longer claim that nobody judged the criterion` | 清单还会说「没人判过」吗 |
| `the next attempt is shown the advisor's section` | 下一轮拿到主线的那一段吗 |
| `the next attempt sees the advisor's own reason` | 下一轮读到主线的原话吗 |
| `the next attempt sees the advisor's judgement of the criterion` | 下一轮读到主线对标准的判定吗 |
| `the reflector is shown the advisor's words` | 复盘读到主线的原话吗 |
| `the advisor's escalation still stops the run early` | 顾问叫停还是叫停得早吗（**回归**） |
| `a criterion the advisor judged as met still closes the loop` | 顾问判「达标」还能闭合吗（**回归**） |

它用**两套独立实现**判定同一件事：一套读**简报**（人能读的那半），
一套读 **`<<MAS_STATE>>` 原始状态** —— 因为简报和状态是**两条
不同的通道**，只到了一条的事实必须被看见。

并且**自证失败** —— 把 `_apply_lead_judgement` 掐掉、把
`lead_advice` 掐掉，门禁必须变红。

### 为什么值得单列一条

这一版修的其实是一个**很常见的假闭环**：判定**发生了**，也**记下来了**，
但它**没有变成行动指令**。

「有人回答过了」和「回答被用上了」之间，隔着的正是这条不变量。
一个说清楚了「缺什么」却没人听的顾问，和一个没被问过的顾问，
在闭环上是**一样的**：下一轮还是不知道要改什么。
