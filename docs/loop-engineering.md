# Loop Engineering：多智能体循环怎么才算闭合

## 一句话

**闭合 = 有一个可被机器判定的结束条件，并且这个判定被记录下来。**

没有这一条，多智能体系统就是一台「烧 token 的永动机」。

## 四个常见的不闭合症状

| 症状 | 表现 | 本项目的对应机制 |
| --- | --- | --- |
| 无验收标准 | 「我觉得差不多了」 | `criteria` 必填，且支持机检规则 |
| 无退出条件 | 一轮轮往下聊 | 闭合/升级/预算三种终态，二选一必须发生 |
| 无过程记录 | 出事无法复盘 | append-only 账本，每轮一条 |
| 无止损 | 走不通的任务反复重试 | 迭代/墙钟/token 三重预算 + 停滞检测 |

## 关键区分：谁的判定

一个循环能不能闭合，取决于**判定权在谁手里**。

- 判定权在模型手里 → 模型说「好了」就是好了，无法复现，无法审计；
- 判定权在引擎手里 → 同一份产物 + 同一份标准，永远得到同一个结论。

因此本项目把验收标准拆成两层：

```
验收标准
├─ 带 check  →  引擎判定（contains / min_chars / regex / json_keys ...）→ 可复现
└─ 无 check  →  模型判定（verifier 给出 pass/note）→ 不可复现，但仍然要给出证据
```

两层都通过才算闭合；模型层没给结论的，按不通过处理。

## 第三层：证据必须来自磁盘（v0.7.15）

前两层还有一个共同的前提没被检验：**模型的产物文本本身也是模型写的**。
所以「产物里写着 `out/report.md` 已生成」和「`out/report.md` 真的在磁盘上」，
在文本机检眼里是同一件事。于是有一类闭环看起来闭合了，实际只是**承诺被当成了事实**：

> worker 说「已把结论写入 `out/report.md`」，产出一段很像样的说明；
> 机检搜文本 → 找不到期望字符串 → 不通过；可一旦期望字符串也出现在那段说明里，
> 机检就判通过——**而磁盘上根本没有那个文件**。

所以 v0.7.15 加了第三层：

```
验收标准
├─ 带 check  →  引擎判定（文本层）
├─ 无 check  →  模型判定（语义层）
└─ 文件级 check →  引擎判定（磁盘层：file_exists / file_contains / file_sha256 ...）
```

磁盘层的判定权**不在模型手里**：文件在不在、字节是多少、摘要是什么，
都是引擎自己去 `stat` 和 `read` 出来的。模型说了不算。

配套还必须有**写侧**：worker 的输出只是一个字符串，它没有别的途径把文件放到磁盘上。
v0.7.15 的写文件协议给了它一条有限、可审计的路——
`<<<MAS:FILE path="...">>>` 围栏块，引擎原样落盘、记账本、拒越界。

只加读侧不加写侧是半个功能（检查永远过不了）；只加写侧不加读侧更危险
（写了也证明不了，只是多了一个能乱写文件的口子）。两层必须一起上。

详见 [`file-checks.md`](file-checks.md)。

## 「机检标准」的写法

一条好标准的特征是：**读者和机器都能独立判定它成立与否。**

| 反例（不可核验） | 正例（可核验） |
| --- | --- |
| 质量要好 | 正文 ≥ 800 字且包含 3 个小节标题 |
| 不要有错别字 | 不包含 `TODO`、`待补充`、`xxx` |
| 结构清晰 | 存在 `## 背景`、`## 方案`、`## 验收` 三个标题 |
| 数据要准确 | JSON 中的 `version` 字段等于 `v0.1.0` |

写不出机检规则，往往说明**目标本身还没想清楚**。这时正确动作不是硬编一条规则，而是把目标拆细，或者接受「这条标准交给模型判定，但要求它给出证据」。

## 闭环的四个不变量

1. **闭合必须可判定**：`status` 只有 `closed` / `escalated` / `budget_exhausted` / `error`。
2. **闭合必须留痕**：闭合的那一轮一定有 `closure` 账本条目，含产物哈希与逐条判定。
3. **不判定不放行**：没有判定 = 不通过。
4. **停不下来就升级**：停滞与预算触顶都要升级人工，而不是继续空转。

## 第六个不变量：闭环必须钉在它判定时依据的字节上（v0.7.88）

前面五条不变量管的是**判定怎么发生**。这一条管的是**判定之后**。

一个闭合的循环声称：**同一份产物 + 同一份标准，永远得到同一个结论。**
但这个承诺只兑现了一半：

* 账本记了交付物**正文**的哈希，**验收标准却只活在引擎的内存里** ——
  事后的读者**没法独立重算**，只能选择相信；
* worker 写出的文件只记了**长度**，没记内容 ——
  事后有人把文件改掉（哪怕改回**同样长度**），账本**一点察觉都没有**，
  循环照样报 `closed / pass`。

这两条是同一个洞：**结论没有被钉在它判定时依据的那份字节上。**
「结论可以重算」这句话，当时只是**关于引擎内部**的；它从来没有
**对账本**成立过。

所以闭环在判定的那一刻，把**它判定所依据的东西**一起封进账本：

```
封存 = {
  完整的验收标准,      # 重算的输入
  交付物的 sha256,      # 重算的输入
  每个写出文件的 sha256, # 事后有没有被改
  逐条判定,            # 重算的结果要和它比对
  判定结论 / 决策 / 工作目录
}
```

之后 `mas seal` 只凭这份封存**重新推导**结论：重读磁盘、重跑机检、
拿结果和封存的判定比对。

### 三条边界，说清楚它证明到哪一步

1. **只由模型判定的标准不能重算。** 模型判过的标准会被封成模型的答案，
   并如实标成 `model-judged` —— **不谎称重算过**。
   封存因此证明的是「**有机检的那部分仍然成立**」。
2. **不能重算不算通过。** 交付物不在了、格式读不懂了，都报成
   `unrecomputable`，**不是** `pass`。
3. **封存是记录，不是公证。** 同时改掉封存和账本的人仍然能造出一份
   能通过复核的封存。它换来的是：**一次普通的事后小改动会变得可见**。

### 三条闭合路径，封存得一样严

主循环、人工交付物（`handback`）、人工文件夹交付（`handback_workspace`）
是三种闭合，判定的标准都是同一套，所以封存也是同一套。

这一点不是一开始就对的 —— 写这一格的时候当场抓到**两个真 bug**：

* 两条人工路径在封存时引用了一个**并不存在**的变量：
  交付物判完了、文件写好了，运行却在写账本的路上**崩掉**；
* 封存记的是**运行自己的目录**，而机检读的其实是**人工编辑的那个目录** ——
  重算读到另一个文件夹的文件，**把没发生过的漂移报成漂移**。

两个都没有测试钉住，因为**没有一个测试向人工路径要过封存**。

### 这条不变量由第 28 项门禁 `closure_seal` 守着

```bash
mas selftest --only closure_seal
```

门禁要求：闭环**确实带上封存**、封存**确实能重算出同一个判定**、
文件被改过**确实被说成漂移**、封存被改过**确实被说成篡改**、
**不能重算的不算通过** —— 而且门禁自己**必须能失败**：
它会把漂移检测故意打断一次，然后确认自己**注意到了**。

## 第七个不变量：结论漂移了，报告必须说出来（v0.7.89）

第六个不变量让结论**可以重算**。
但“可以重算”有两个实现的地方：

* `mas seal` —— 一个**专门的命令**，给出“这些闭环还成立吗”的答案；
* `mas report` —— **人真正会看的那个屏幕**。

在 v0.7.89 之前，**第二个地方不存在**。
报告从来不看封存，所以它继续写“已解决”、
“机器闭环”，屏掉一个**结论的字节已经被改过**的闭环。

这是一个很具体的失败：

* 用户跑完一个任务，看报告：“已解决。”
* 两天后他修了一下交付物里的文件。
* 再看报告：**仍然是“已解决。”**。

**能证明漂移的能力，却没有被主视图消费 —— 那就等于没有。**

### 报告里多了什么

| 位置 | 之前 | 现在 |
| --- | --- | --- |
| 问题概览的状态列 | 已解决 | **结论已漂移** |
| 运行概览的状态列 | `OK 已闭环` | `DRF 结论已漂移（已闭环）` |
| 运行概览的来源列 | 🤖 机器闭环 | **⚠ 结论已漂移** |
| 报告顶部 | 只说闭环率 | 多一行“封存复核：N 条封存中…” |
| 每个运行的详情 | 没有 | **封存：⚠ 结论已漂移** + 哪个文件被改过 |
| JSON 载荷 | 没有 | `seal: {sealed, holds, drifted, ok, states}` |

**封存不存在的运行不被报成漂移。**
封存是 v0.7.88 才加的，就算靠现的旧闭环没有封存，
它也**不是被改过的**。“没有封存”和“封存漂移”
是两件事，报告分得开。

### 为什么不能只做到 `mas seal`

可以，`mas seal` 已经能答这个问题了。但它是一个
**专门命令**，一个专门命令能做的事，**主视图不做就等于没有**。

而且这里还有一个细节：**报告是一个几万行的文本**。
一个人会自然先扫“问题概览”那记表 ——
**所以漂移必须出现在那里**，而不是只在运行详情里。
本版本就是这个原则：**漂移在摘要表里就看得见。**

### 这条不变量由第 29 项门禁 `report_seal` 守着

```bash
mas selftest --only report_seal
```

门禁要求：健康的闭环被报成“仍然成立”、
被改过的闭环在**问题概览**、**运行概览**和
**运行详情**里都说出“结论已漂移”、
JSON 载荷里带上复核结果 —— 而且门禁自证**能失败**：
它会把报告的封存检查故意打坏成“永远成立”，
然后确认自己已经**分不出**健康的闭环和被改过的闭环。

## 第八个不变量：一次批准是错的，这件事在报告里必须说得出来（v0.7.90）

第七个不变量让“结论漂移”可见。
但还有一类事实，它不是关于运行的，而是关于**人的决定**：

* 你批准了一个草稿（`draft_approve`）；
* 你发现它是错的，把批准撤回去（`draft_undo`）；
* 文件被退回去了，账本里留下了痕迹。

**你的批准曾经是错的——这一点还记得着。**
但在 v0.7.90 之前，`mas report` 从来没看过它：
`run_summary()` 根本不读 `draft_approve` / `draft_undo` 那两类行。

这里有一个很具体的失败：

* 你运完一个任务，看报告：「已解决 · 机器闭环」。
* 三周前你撤回过两次错批准，账本里醒着。
* 再看报告：**还是「已解决 · 机器闭环」**。

你看到的是一个干净的机器，背后却是一段**错的历史**。

**能证明「哪些批准是错的」能力，却没有被主视图消费 —— 那就等于没有。**
（与第七个不变量同型：能力存在，主视图不消费。）

### 撤销属于工作区，不属于任何一次运行

这里有一个容易造成脏数据的地方：
**草稿和运行之间没有关联键。**
同一个草稿可以被批准、撤销、再批准，
自始至终没有任何一次运行参与过。

所以“把它塞进某个线程”会**凭空造出一个关系**，
而“塞进某次运行”同样是假的。
它是**工作区级的事实**，所以报告把它放在
**报告顶层**、单独一节，不硬塞进任何一次运行。

### 报告里多了什么

| 位置 | 之前 | 现在 |
| --- | --- | --- |
| 报告顶部 | 没有 | **撤销回收：N 次批准被撤销** |
| 报告正文 | 没有 | **「被撤销的批准」**一节（草稿 / 文件 / 次数 / 退回行数） |
| JSON 载荷 | 没有 | `undos: {records, unmatched, totals, drafts}` |
| 顶部计数 | 没有 | `approvals_taken_back` / `drafts_taken_back` / `lines_reverted` / `undos_unmatched` |

**只有人工决定、没有任何运行的账本，不再被说成「账本为空」。**
这是一句假话：账本里满是错批准。
现在这个情况会说「这台机器上还没有跑过任何一次闭环，
但账本里记着人工的决定」，并指向 `mas undos`。

### 配对逻辑不重写

`mas.undos` 已经把配对做对了（位置式栈，
撤销取回**最近一个还立着的批准**）。
报告只是**读**这个答案，不重新实现一质。
因此**配不上的撤销被计数而不隐藏**（报告顶部会单独说出来），
而且**不猜**。

### 这条不变量由第 30 项门禁 `report_undo` 守着

```bash
mas selftest --only report_undo
```

门禁采用**双读法**：一条读报告，
另一条**绕开报告**、直接数账本行里的批准/撤销配对，
两边必须一致。门禁还**自证能失败** ——
把报告的撤销计数打坏成「永远等于合法」，
门禁必须发现它已经分不出错批和对批。

## 第九个不变量：记录被篡改了，报告必须说出来（v0.7.91）

第八个不变量让「你的批准曾经是错的」可见。
但还有一类事实，它不是关于**一次决定的对错**，
而是关于**记录本身有没有被改过**：

* 你批准了一个草稿 → 链里一条哈希相连的记录；
* 你把批准撤回去 → 又一条；
* 有人用编辑器改了其中一条的 `note` → **链不再自洽**。

**你的决定记录被改过了 —— 这一点还记得着。**
但在 v0.7.91 之前，`mas report` 从来没看过它：
`mas/report.py` 的 `import` 里连 `mas.audit` 都没有。

这里有一个很具体的失败：

* 你运完一个任务，看报告：「已解决 · 机器闭环」。
* 有人改过你的审计链（或者删了整条链）。
* 再看报告：**还是「已解决 · 机器闭环」**。

**能证明「记录没被改过」的能力，却没有被主视图消费 —— 那就等于没有。**
（这是同型洞的第三个：封存、撤销、审计链。）

### 报告怎么找到要查的链

**从账本行自己反推，而不是猜目录。**
每一行带 `workspace` 字段的记录都知道自己属于哪个工作区，
报告就查**写下那些决定的那几条链** —— 不多不少。

`mas status` 是猜 `<state_dir>/artifacts` 的。
报告若也这么猜，就会漏掉那些自带工作区的运行，
也会去读不属于任何人的链。**报告比 status 更精确。**

### 链整个不见了，怎么发现

一条被**整体删掉**的链，读它是读不出问题的 —— 没有内容可读。
但**账本里还留着那个决定**，所以报告会把

> 工作区 X 的账本记着 N 条人工决定，但审计链不见了

当成一个**记录缺口**点出来。
**缺失也必须被说出来** —— 否则删链就成了最省事的掩盖办法。

### 报告里多了什么

| 位置 | 之前 | 现在 |
| --- | --- | --- |
| 报告顶部 | 没有 | **审计链复核：N 条链、M 条记录，K 个问题** |
| 报告正文 | 没有 | **「审计链复核」**一节（逐条点名哪个链、哪条记录被改过） |
| JSON 载荷 | 没有 | `audit: {workspaces, chains, chain_count, entries, problems, problem_count, ok}` |
| 顶部计数 | 没有 | `audit_chains` / `audit_entries` / `audit_problems` |

**退出码语义不变。** 报告仍然以 0 退出 ——
报告是给人看的，**报警的出口是 `mas audit` 和 `mas seal`**。

### 这条不变量由第 31 项门禁 `report_audit` 守着

```bash
mas selftest --only report_audit
```

门禁采用**双读法**：一条读报告的 Markdown，
另一条**绕开报告**、直接读 JSON 载荷里的链和问题，
两边必须一致。门禁还**自证能失败** ——


## 第十个不变量：自检不得污染被它检查的那台机器（v0.7.92）

前面九条不变量都在讲**运行时**。
这一条讲的是**检查运行时的那段代码**本身。

自检要证明「撤销是真的把文件退回去了」，
所以它**必须真的批准一次草稿、真的撤销一次**。
而「批准」是一次**人工决定** ——
人工决定要记进**主账本**。

于是（v0.7.92 之前）：

```
mas selftest  →  ~/.mas/ledgers/runs.jsonl 多出若干行
                 workspace 指向一个当场就被删掉的临时目录
```

行留下了，**链没了**。于是：

```
mas report →  账本说「人批准过什么」
              链说「没有这条链」
              → 报出几百个审计问题
```

**那几百个「批准」是测试自己批的。**
用户跑过一次自检，这台机器就会**永远**报几百个问题，
而且**分不出**哪个是真问题、哪个是测试留下的。

> **一次会改变被测机器状态的自检，不是自检 —— 它是一个带退出码的副作用。**

### 三条边界，说清楚它证明到哪一步

| 边界 | 含义 |
| --- | --- |
| **账本行数与字节都不变** | 不是「差不多一样」，是**行数一致、文件摘要一致** |
| **环境变量原样还原** | 一道门禁改了 `MAS_STATE_DIR` 却没改回去，就会**悄悄重指向后面所有门禁**，把下一个泄漏盖住 |
| **自检的决定仍然被记录** | 隔离不能顺手把记录也丢了 —— 否则证明「审计链有效」的那几道门禁**等于什么都没证明** |

第三条是这一条不变量最容易做错的地方：
**隔离不是遗忘**。记录要留在**测试自己的**账本里。

### 套件级兜底

除了逐门禁隔离，整轮自检**前后**还会对比机器的状态目录：

* 任何落在临时目录之外的改动 → **被点名**；
* 并且**让整轮自检失败**。

这样以后**新增**的门禁即使忘了隔离，也会被立刻抓住 ——
而不是等它在用户机器上跑了几百轮之后。

### 这条不变量由第 32 项门禁 `selftest_isolation` 守着

```bash

```

门禁**自证能失败**：把隔离打坏成「什么都不隔离」，
门禁必须发现它已经分不出「干净的一轮」和「脏的一轮」。

## 第十三个不变量：文档还是文本（v0.7.94）

写 v0.7.93 发布说明时，文本是经过一个把反引号当**转义符**的 shell
产出来的。所以：

| 写的是 | 得到的是 |
| --- | --- |
| `budget` | 一个**退格符** |
| `tickets` | 一个**制表符** |
| `reason_text` | 一个**回车**，后面的 `eason_text` 又少了首字母 |
| ```bash | ``bash |

伤害很小，而且在渲染后的 Markdown 页面里**几乎看不出来**：
句子还是那个句子，代码块还像个代码块。
但**磁盘上的文件已经坏掉了** —— 字母的位置上是一个控制字符，
缩进的地方是一个 Tab。

而它**发布出去了**，因为**没有任何东西在看**。

这正是关键。一份文档是初学者第一个打开的文件。
一份里面带退格符的文档不是文档，
它只是一个**大致是文本**的文件。

而本项目自己的规则是：**没人检查的能力，就算没有** ——
所以这个项目里的每一个坑都有一道门禁，这一个也在等。

### 这条不变量说了什么

| 边界 | 含义 |
| --- | --- |
| **没有控制字符** | 退格符、裸回车、其他控制字符 —— 都不是文本 |
| **没有残留的 Tab** | 附言里的 Tab 是被吃掉的字符；围栏里的 Tab 可以容忍 |
| **代码围栏完整** | 开头围栏只能写语言（或不写），闭合围栏不能带文字，每个围栏都要有尾 |

### 为什么这条需要门禁

不是因为"规范"。是因为"规范"**已经无声地破坏过一次**，
并且破坏的方式是"把字母吃掉" —— 这个方式在渲染后看不出来。

所以门禁不只看"有没有异常"，它还要**自证能失败**：
把一份文档**故意破坏**（注入一个退格符），
门禁必须发现它已经分不出"正常文本"和"被磨损的文本"。

## 第十四个不变量：复盘报告必须读每一条账本行（v0.7.95）

账本是真相，报告是账本的投影。
但投影**漏掉了六种行** —— 于是报告读出来的账本，
比实际的账本**少了一半内容**。

账本表的最后一列叫「摘要」，内容来自 `mas/report.py` 的 `_short_detail()`。
它按角色分派：`closure`、`planner`、`review`、`reflector`、`handback`、
`draft_approve`、`draft_undo`…… **有六个角色根本没有分支**：

| 角色 | 它记录的是什么 | 之前渲染成 |
| --- | --- | --- |
| `write` | 引擎实际写了哪些文件、多少字节、新建还是覆盖 | **空白** |
| `draft` | 循环提议了哪个改动、等人批 | **空白** |
| `truncated` | 回答写到一半被截断，所以要重试 | **空白** |
| `reask` | 因为哪几条标准没过而补问 | **空白** |
| `reask_failed` | 补问失败了 | **空白** |
| `lead` | 顾问给出的建议 | **空白** |

分派落到最后是 `return ""`。
表格里那一行**在** —— 有序号、有时间、有运行号、有角色 ——
唯一说「发生了什么」的那一列**是空的**。

### 为什么这一条特别要紧

`write` 行是唯一一行能回答
**「这个智能体到底改了我机器上的什么」** 的记录：
哪个文件、多少字节、是新建还是覆盖。

而它在报告里**完全看不见**。

于是：**写了三个文件的运行，和什么都没写的运行，在报告里长得一模一样。**

一个审计者打开报告，看到「闭环了，通过 3/3」，
他知道交付物是对的；他**看不到**这三个文件是哪三个、
也没法确认引擎有没有顺手改了他没要求改的东西。

这和前五个洞是同一个家族 ——
**能力存在，主视图不消费**：

| 版本 | 能力 | 之前的状态 |
| --- | --- | --- |
| v0.7.89 | 封存 | 报告不看 |
| v0.7.90 | 撤销 | 报告不看 |
| v0.7.91 | 审计链 | 报告不看 |
| v0.7.93 | 工单队列 | 报告不看 |
| v0.7.94 | 草稿队列 | 报告不看 |
| v0.7.95 | **每一条账本行** | **报告不看** |

### 这条不变量说了什么

| 边界 | 含义 |
| --- | --- |
| **每种角色都要有话说** | 引擎写得出的每一种行，摘要都**非空** |
| **写入要点名** | 文件名、字节数、新建 / 未写入；一次都没写成时说「没有文件被写入」，不留白 |
| **草稿要点名** | 草稿号与文件 |
| **截断要点名** | 截断的原因、已用 tokens、将重试 |
| **补问要点名** | 哪几条标准没过 |
| **顾问要点名** | 顾问说了什么 |

`role_reading()` 也补上了 `draft` 的中文读法「提议改动」——

```bash

```

门禁读**引擎会写出的每一种账本角色**，要求每一种的摘要都非空，
而且**导出的表格里没有任何一行摘要为空**。

## 第十五个不变量：交付物清单必须同时到达命令行和 MCP（v0.7.96）

### 洞在哪里

### 这条不变量说了什么

## 第十六个不变量：闭合的判定必须同时到达命令行和 MCP（v0.7.97）

`mas doctor` 只体检配置。`mas run` 只跑一次任务。**MCP 里没有任何一个工具能回答「这套系统闭不闭合」**——而这正是 LoopEngineering 自己的核心命题。

### 洞在哪里

报告能展示所有数字：跑了多少次、闭合率多少、有几张工单在等人、有几份草稿没批。

但**「闭合」的判定规则从来没被写下来放到读者够得着的地方**。拿着整套 MCP 工具的智能体读完报告的所有数字，仍然得**自己**在脑子里把这几格拼起来，才能回答「这活儿干完了吗」——而不同的人拼法不一样。

换句话说：报告**展示**闭合，判定**不存在**。一个能把每一个数字都摆出来的系统，不一定知道自己算不算完。

### 这条不变量说了什么

| 边界 | 含义 |
| --- | --- |
| **一份判定，两个界面** | 判定住在 `mas/report.py`：`closure_verdict()` 算，`format_closure()` 渲染，`closure_verdict_for()` 是两个界面共用的唯一入口 |
| **闭合 ≠ 跑成功** | 闭合是「没有任何东西在等」：没有未闭合的运行、没有开着的问题线索、没有等人工接手的工单、没有等人批准的草稿、没有对不上的封存、没有验不过的决策链 |
| **每一格单独报数** | 只说「没闭合」是把读者撵去自己找；说「3 份草稿等人批准」才告诉他该干什么 |
| **空账本不算闭合** | 账本是空的不是「闭环完美」，是「还没跑过」——这两种情况必须用不同的措辞，冒充就是撒谎 |
| **只读** | 判定读账本、读工单队列、读草稿队列；它**不启动任何一次运行** |

新工具 `mas_closure`（MCP），新命令 `mas closure`（命令行，未闭合时退出码 2）。

| v0.7.93 | 工单队列 | 报告不看 |

| v0.7.95 | 每一条账本行 | 报告不看 |

| v0.7.97 | **闭合的判定** | **两个界面都没有** |

### 这条不变量由第 38 项门禁 `closure_verdict` 守着

```bash
mas selftest --only closure_verdict
```

门禁要求：`mas_closure` 被公布、干净的闭合运行判为闭合、留给人做的工作判为未闭合并点名是哪一格、空账本不算闭合、**MCP 和命令行的答案完全一致**、原因以数据返回。

门禁**独立实现两遍判定**（`_closure_verdicts` 与 `_closure_verdicts_independent`），并**自证能失败**：把共享判定替换成「永远说闭合」，门禁必须报警。

## 第十七个不变量：闭合的粒度是问题，不是尝试（v0.7.98）

v0.7.97 把闭合判定放进了 `mas/report.py`，命令行和 MCP 共用一份。这一条是它的**续集**：
判定住下来了，但**数错了东西**。

### 洞在哪里

报告把运行按**问题**分组：一次失败后被 resume 成功的问题，是**一个问题**，
闭合了。线程判定的规则一直是对的——**最后一次尝试说了算**，后来的尝试取代前面的。

可是闭合判定数的是 `totals["not_closed"]`，也就是**没闭合的尝试数**。
于是同一份报告能同时说两件事：

```
threads:    [('T-1', closed=True)]        <- 问题已闭合
VERDICT:    ok=False ['runs_not_closed']   <- 还有东西在等
```

**一份报告，两个答案。**

更要命的是后果：**失败 → resume → 成功**这条核心工作流，永远拿不到 `ok=True`。
问题队列只会越积越多，而一个永远不清空的队列，教会读者忽略它——
这正是这个项目一直在修的那类失败，换了个马甲。

### 这条不变量说了什么

| 边界 | 含义 |
| --- | --- |
| **粒度是问题** | 一次失败后被成功尝试**取代**，问题就是闭合的 |
| **历史不是待办** | 被取代的失败仍然计数，但不算「还在等」 |
| **一份报告一个答案** | 报告的线程判定和闭合判定不能对同一个问题说出相反的话 |
| **两个闭环率，两个粒度** | 尝试闭环率和问题闭环率**各自报出自己的粒度**，不混着说 |

### 三个数，各有各的用处

| 数 | 是什么 | 例子（失败→成功） |
| --- | --- | --- |
| `not_closed` | **所有**没闭合的尝试。历史。 | 1 |
| `not_closed_open` | **仍在开放问题里**的失败尝试。待办。**判定建在它上面。** | 0 |
| `not_closed_superseded` | 已被后来成功尝试取代的失败。历史的一部分。 | 1 |

另外新增 `problem_closure_rate`（已解决问题 / 全部问题），
和原有的 `closure_rate`（已闭合尝试 / 全部尝试）**并存**——
一个是问题的闭环率，一个是尝试的闭环率，读者一眼能看出差在哪。

### 这是同一族的第九个洞

前八个的形状是「能力在账本里，主视图不读它」「能力在一个界面里，另一个界面看不见」
「判定规则只存在于人的脑子里」。这一次的形状是：**判定存在了，但数错了粒度，
于是报告自己跟自己打架。**

| 版本 | 能力 | 之前的状态 |
| --- | --- | --- |
| v0.7.89 | 封存 | 报告不看 |
| v0.7.90 | 撤销 | 报告不看 |
| v0.7.91 | 审计链 | 报告不看 |
| v0.7.93 | 工单队列 | 报告不看 |
| v0.7.94 | 草稿队列 | 报告不看 |
| v0.7.95 | 每一条账本行 | 报告不看 |
| v0.7.96 | 交付物清单 | MCP 看不到 |
| v0.7.97 | 闭合的判定 | 两个界面都没有 |
| v0.7.98 | **闭合的粒度** | **报告和判定互相打架** |

### 这条不变量由第 39 项门禁 `closure_supersede` 守着

```bash
mas selftest --only closure_supersede
```

门禁要求：被取代的失败**不占着队列**、最后失败的问题**仍然开着**、
**报告和判定不能给相反的答案**、被取代的失败**仍然计作历史**、
**两个闭环率都报出自己的粒度**、**命令行和 MCP 给出同一个答案**。

门禁**独立实现两遍判定**（`_supersede_verdicts` 与 `_supersede_verdicts_independent`），
并**自证能失败**：把判定**故意打坏**成「每次失败都算待办」（旧口径），
门禁必须发现「失败后被成功取代」的问题又被报成未完成。

## 第五个不变量：并行选优必须是确定的（v0.7.64）

当多个 worker 同时产出候选时，引擎要挑一个交出去。这个「挑」一旦掺进
**赛跑的偶然性**，闭环就漏了：

- 候选池按**完成顺序**回填结果 → 谁先跑完谁赢；
- 平局反向打破 → 同一个任务两次跑出两个交付物；
- 排名把**正文长度**排在机检之前 → 更长但一条标准都没过的稿子赢。

这三种情况运行**照样报成功**——状态是 `closed`，账本也是齐的，只有
交付物悄悄换了。**一个会悄悄换答案的闭环，是不能复盘的闭环。**

所以引擎的排序是死的：`（通过的机检数，正文长度，最小序号）`。同分时取
序号更小的那个，候选池的结果按**投进去的序号**回填，跟谁先跑完无关。

这条不变量由第 6 项门禁 `parallel_pick` 守着（`mas selftest`）。门禁把
赛次**排好**而不是靠运气：用事件链把三个候选的完成顺序钉成逆序，
再让两个候选的机检数和长度完全相同（只能靠序号分胜负）、第三个更长但
一条机检都过不了。任何一处排序被改动，门禁当场变红。

```bash
mas selftest --only parallel_pick
```

## 第六个不变量：没闭合的运行必须留下人能接手的东西（v0.7.65）

闭环跑不出来的时候，它不甩手，它**升级**：开一张票据，等人来接。这个承诺
有三半：

1. 升级，而不是空转 —— 引擎确实这么做了；
2. 开票据，而不是只写一句「失败」 —— 引擎确实这么做了；
3. **票据带够让人接回来的上下文** —— 这一半从来没人守。

第 3 半看着像细节，其实是闭环的最后一环。一张只写了「停滞了」的票据，
人接回来之后拿到的是**一个没有验收标准的循环**：谁说了算？评审。
于是循环照样能闭合、照样报成功 —— 只是它已经不是用户要的那个循环了。
**一个接不回来的闭环，升级就只是把失败换了个地方存。**

所以票据必须带齐：

| 字段 | 人拿它干什么 |
| --- | --- |
| `goal` / `title` | 知道自己在接什么问题 |
| `criteria` | **带机检的**验收标准 —— 这是最要紧的一条 |
| `last_artifact` | 看到最后一版长什么样 |
| `issues` / `reason` | 知道卡在哪、为什么停 |
| `history` / `runs` / `stagnation` | 知道已经烧了几轮、值不值得接着烧 |
| `status` | 知道这次是升级、预算耗尽还是出错 |

`criteria` 之所以最要紧，是因为 **`engine.resume()` 用的就是票据里的
`goal` 和 `criteria`**。标准在票据上丢了或者只剩散文，接回来的循环就没有
标准了 —— 闭环在这一刻静悄悄降级。

这条不变量由第 7 项门禁 `handover_ticket` 守着（`mas selftest`）。门禁的
办法很直接：**把票据用起来**。它让运行升级、开出票据，然后拿票据里的
标准喂回 `engine.resume()`，要求循环真的闭合。这个检查里的 verifier
**永远答 fail**，所以闭环只能靠票据带回来的**机检** —— 模型糊弄不过去，
票据丢了标准就接不回来。票据和账本还得互相指得到对方，否则人找不到问题。

顺带一提：这道门禁在第一次跑的时候当场抓到一个真 bug —— 票据的字段在两条
升级路径上不一致（停滞升级少了 `status`）。现在两条路径共用一个 payload
构造器，**票据只有一个形状**。

```bash
mas selftest --only handover_ticket
```

## 接手：看得见成果，也要换一份预算

票据带齐了上下文，**接手的运行却用不上那份上下文**。这一节是 v0.7.66
补上的最后一环。

### 四个真缺陷

| 现象 | 根因 | 现在 |
| --- | --- | --- |
| 预算触顶的运行被归到「循环自己闭不上」 | token 分支只设了 `decision`，没设状态，被升级分支盖掉 | 预算触顶就是 `budget_exhausted` |
| 接手的运行看不见上一轮的交付物 | 续跑把尝试计数重置成 1、问题清单清空 | 上一轮的交付物交给接手的 worker，并要求在它基础上改 |
| 预算触顶的票据，续跑立刻再次触顶 | `resume()` 完全复用本机配置的预算 | 三条上限按这一轮单独给，且不漏进下一轮 |
| 屏幕上那句「接着干」是死路 | 打印的命令继承了同样的上限 | 续跑命令带上更宽的那一条上限 |

「预算触顶」和「循环闭不上」需要**完全不同**的反应：前者要加预算，后者要
换计划。混在一个队列里，人就会一直查错方向。

### 预算可以按这一轮给

```bash
mas resume T-20261116-064911-7ab1 \
  --max-iterations 8 --deadline-sec 60 --max-tokens 20000 \
  --note "你的意见"
```

这三个旗标**只影响这一轮**，不改本机配置，也不会漏进同一引擎的下一轮。

屏幕上的续跑命令会**自己带上放宽后的上限**（外加一个下限，保证宽出来的
预算真的能干活，而不是把同一堵墙放大一点再撞一次）。旗标名和命令行一致：
`--max-tokens`，不是 `--max_tokens` —— 屏幕上的命令必须能粘贴就能跑。

### 这条不变量由第 8 项门禁 `takeover_handover` 守着

```bash
mas selftest --only takeover_handover
```

门禁把四种停法（轮数 / token / 墙钟 / 后端报错）各跑一遍，要求：

* 每种停法都留下一张说清原因的票据；
* 票据记着这一轮跑在什么预算下；
* 续跑命令带着更宽的预算；
* **接手的 worker 真的看得见上一轮的交付物**；
* **用新预算接手后循环真的闭合**，而且是靠票据带回来的**机检**闭合的。

这道门禁在第一次跑的时候当场抓到两个真 bug：屏幕上的续跑命令旗标名写错
（粘贴就报错），以及放宽逻辑在退化预算下会让续跑再次原地撞墙。

## 人写的交付物，也要走同一道门（v0.7.67）

工单队列以前只有**一个**答案：「续跑，让机器再试一次」。

但循环升级的真实场景往往是反过来的：**人已经把答案写好了**。
模型反复产出不合格的产物，人改好了它 —— 然后系统没有地方放这份东西，
于是那份工作被扔掉，让机器从头再推导一遍，通常还更差。

「接手的运行看得见上一轮的成果」（v0.7.66）解决的是**机器接着干**。
v0.7.67 补上的是**人接着干**：

```bash
mas handback T-20261116-075440-8aae --file 我的交付物.md
```

### 三条性质，让它是一个闭环而不是一个橡皮图章

1. **同一套标准做判定。** 验收标准是从工单上取回来的 —— **就是这件事
   当初写下的那套**，不是重新解释一遍。带机检的标准由机检说了算，
   **评审员不能推翻它**（和正常运行时一模一样）。
2. **不合格的接回不闭合。** 失败项写回票上，工单**留在人工队列里**。
   一次被拒的接回是第二次尝试，不是一次结单。
3. **评审挂了不毁掉人写好的东西。** 机检在调用评审**之前**就已经判完了。
   后端这时挂掉，只会把「评审失败」如实记下来 —— 一份人工写好的交付物
   不会凭空消失。

### 为什么第 3 条是被抓出来的，不是想出来的

第一版的捕获范围比主循环窄：只接住了 `ProviderError`。
探针里让 provider 抛一个普通 `RuntimeError`，结果**手写的交付物直接
连同整个命令一起崩了** —— 而这条路径存在的全部意义，就是**保护人已经
写好的东西**。现在它和主循环一样宽。

### 一句话记住

> 升级不是失败，是**换一个人接手**。
> 接手的人可能是机器（`mas resume`），也可能是你（`mas handback`）——
> **两条路走的是同一道门。**

### 这条不变量由第 9 项门禁 `handback_closes` 守着

```bash
mas selftest --only handback_closes
```

门禁要求：

* 合格的人工交付物**真的闭合**，而且是靠票据带回来的**机检**闭合的；
* 通过的交付物**落到磁盘上**，票据归档成 `handback`；
* 不合格的交付物**不闭合**，失败项留在票上，工单**还在队列里**；
* **评审挂了**，机检已经通过的那份交付物**照样闭合**。

## 报告要看得见「人写的那一步」（v0.7.68）

v0.7.67 让人写的交付物能把环闭闭上。但那份成果在报告里
是**看不见的** —— 报告只认机器跑出来的记录，人交回的东西
在账本里留了一行，却读不出结论。

这一版把这条缝补上。而且是**当场抓到两个真 bug** 才开始的。

### 两个被量出来的缺陷

**缺陷一：环闭了，报告说没闭。**

探针里让人工交回一份合格的交付物，然后去读报告，结果是：

```
closed=False  closure_rate=0.0  problems_open=1
```

根因有两个：

1. 人工交回的账本条目**缺** `closed` / `goal` / `title` /
   `decision` / `files` 等字段，报告根本读不到结论；
2. **分数挂在 `handback` 行上，报告却只读 `closure` 行**。

现在两边都补上，并且报告在**没有机器 closure 记录时**
会回退去读 handback 的分数。

**缺陷二：失败过一次，就永远待处理。**

旧的线程闭合规则是：

```python
closed = all(m.get("closed") for m in members)   # —— 旧的，错的
```

意思是「线程里每一次运行都闭合了，线程才闭合」。
但环闭的实际语义是**最后一次尝试闭合了，就算闭合** ——
人写完、或者后面跑成了，就不应该被永远挂在「待处理」里。

现在线程记录里多了两个字段：`closed_by`（是哪一次运行闭合的）
与 `handback`（是不是人工交回闭的）。

### 报告里新增的「来源」列

问题概览与运行概览两张表都多了一列：

| 来源 | 含义 |
| --- | --- |
| `🤝 人工完成` | 这个问题是人写的交付物关上的 |
| `🤖 机器闭环` | 这个问题是机器自己跑闭合的 |

人工交回的运行还会带一个单独的验收小节（「人工交付物的验收判定：」），
逐条列出通过/未通过，并附上**人的意见**。

### 词汇分开了

机器闭合记 `close`，人工交回记 `handback` —— 两者在账本、报告、
replay 里是**不同的词**。你不再需要从推断里面猜「这次是谁关的」。

### 一句话记住

> 闭环不只有一种形态。
> **机器闭合是一种，人工交回也是一种** —— 而报告必须把两者都说清楚。

### 这条不变量由第 10 项门禁 `handback_report` 守着

```bash
mas selftest --only handback_report
```

门禁要求：

* 人工交回的闭合在报告里是**已解决**的问题，而不是待处理；
* 报告里带着**验收结果**、**人的意见**和**来源**；
* `mas replay` 也标出人工的那一步；
* **被拒绝的交付物不能消失** —— 失败不许从报告里消失。

### 为什么要加第 10 项门禁（这是反证查出来的）

第 9 项门禁 `handback_closes` 看的是**引擎**：人写的交付物能不能按同一套标准闭合。
但**没有任何门禁看报告层**。

所以我们做了**反证**（mutation testing）：拿报告层的六个行为分别破掉，
再看有没有门禁会报败：

| 变异 | 现在被捕获吗 |
| --- | --- |
| 丢掉 handback 的 `closed` 标志 | 是 |
| 决策词从 `handback` 改成 `close` | 是 |
| 报告不再读 handback 的分数 | 是 |
| 线程闭合回到「所有成员都闭合才算」 | 是 |
| 报告忘掉是哪一次运行闭的 | 是 |
| 来源恒说机器 | 是 |

第一次做这个实验时，**六个变异一个都没被捕获** —— 第 9 项门禁一个都拿住。
这就是新门禁的动机：**门禁不仅要证明引擎对，还要证明读者看到的是对的**。

## 人这条路：文件夹交回

前面讲的都是**机器**怎么闭合。但真实世界里最常见的情况是**人已经把答案写好了**。

v0.7.67 的文本交回接的是**一段文字**。而这个循环真正跑的任务写的是**文件**，
验收标准也是**读磁盘的文件机检**。人改这样的任务，做的事是**打开文件改**；
旧的文本交回却要求人把文件内容**粘进命令行**。

这是**第二份工作**，而复制的这一份正好是容易出错的那一份：
**忘了一行，交回就被拒绝** —— 而拒绝的原因与答案本身无关。

### 交付单位是文件夹

```bash
mas tickets
# 在这里改：C:\Users\me\mas-workspace\H-20261116-130330
# 改完交回：mas handback T-20261116-130330-d623 --workspace "C:\Users\me\mas-workspace\H-20261116-130330"

mas handback T-20261116-130330-d623 --workspace "C:\Users\me\mas-workspace\H-20261116-130330"
```

人在**原地方**改文件，交回的是**那个文件夹**。交付物由文件自动生成
（文件清单 + 小文件的正文），**不用手工粘贴**。

### 草稿语义：判定前不写盘

和文档编辑器一个规矩：

1. 文件夹按**现在的样子**被读取（人的改动已经在里面了）；
2. 它按**票据上当初写下的那套标准**判定，机检读到的是**overlay**
   （盘上现在的字节），**什么都不写**；
3. **只有通过了**的交付物才被写回 —— 而且落在**人改过的那个文件夹里**，
   不是第二个文件夹。

**被拒的交回，磁盘原样不动，也不写交付物。**
人改的工作是这个人的，不该被一次失败的验收丢掉。

### 这条不变量由第 11 项门禁 `folder_handoff` 守着

```bash
mas selftest --only folder_handoff
```

门禁要求：

* 文件机检读到的是**人改过的内容**，不是循环留下的旧内容；
* 文本机检看得到**文件的正文**，交付物是从工作生成的，不是手打的；
* **被拒时磁盘字节不变**，且**不写交付物**；
* 接受时交付物落在**同一个文件夹**，offer 包含**全部文件**；
* 票据**写着那个文件夹**，人不用自己去找。

### 为什么要加第 11 项门禁（这是反证查出来的）

第 9 项门禁看**引擎**，第 10 项门禁看**报告**，**没有任何门禁看人这条路**。

所以我们做了**反证**：拿文件夹交回的六个行为分别破掉，再看有没有门禁会报败：

| 变异 | 现在被捕获吗 |
| --- | --- |
| 机检去读另一个文件夹 | 是 |
| 交付物丢掉文件正文 | 是 |
| 被拒的交回也写交付物 | 是 |
| offer 只取第一个文件 | 是 |
| 交付物落到第二个文件夹 | 是 |
| 票据忘记工作区 | 是 |

第一次做这个实验时，**六个变异一个都没被捕获** —— 前面十项门禁一项都拿住。
这就是新门禁的动机：**人这条路也是一条路，它也得被守住**。

## 交付物本身也要看得见：内容级机检（v0.7.70）

前面讲的所有文件级机检，搜的都是**文件的字节**。

这在「文件里有一行这句话」上是够用的。但对**每一种正文不是明文的格式**，
它是**瞎的**：

* PDF 把文字放在**压缩流**里 —— 文件的字节里根本没有那些字；
* `.docx` / `.xlsx` / `.pptx` 本身**就是 zip 包** —— 文字在包里的成员里；
* 图片里**没有文字**，但它有**格式**、有**尺寸**、有**文件头**。

于是**交付物是 PDF 的任务，机检根本判不了**。
标准落回模型手里，模型说一句「looks fine」，
一条**没人查过的标准**就被关上了 —— 这是**假闭合**，比不闭合更糟。

### 六个新的内容级机检

| type | 含义 |
| --- | --- |
| `content_contains` | 文件**内容**含给定字符串 |
| `content_not_contains` | 文件**内容**不含给定字符串 |
| `content_regex` | 文件**内容**命中正则 |
| `content_lines_min` | 内容**非空行**数下限 |
| `content_min_chars` | 内容**字符数**下限 |
| `content_format_is` | 文件**格式**等于给定格式 |

底层是 `mas/content.py`，**只用标准库**，**不执行文件里的任何东西**：

* `detect_format(path)` —— **magic bytes 优先，扩展名兜底**。
  扩展名会撒谎，`.txt` 里装的是 PDF，那它就是 PDF。
* `extract_text(path)` —— 取出读得出来的文字：PDF 解 FlateDecode 流并抽
  `(...) Tj/TJ` 字符串；Office 文档解 zip 成员并**剥掉 XML 标记**；
  zip 读成员；图片没有文字但**读得开**。
* `describe_file(path)` —— 一张事实表：格式、大小，以及格式自己的事实
  （PDF 的**页数**、Office 的**成员数**、PNG/GIF/BMP 的**像素宽高**）。

### 最要紧的一条：读不出内容 = 不通过

按第一层的纪律，「判不了」应该是 `unjudged`。**这一层不一样。**

`unjudged` 会**回到模型手里**。而模型对「这个文件看起来没问题」这句话
是**不会拒绝**的 —— 于是那条标准被**一句话**关上了。

所以内容级机检读不出内容时判 **`pass: false`**。
标准留在那儿，**等人来修**。

### 草稿语义同样适用

要写的新文件，机检按**将要写进去的那份字节**判（overlay）。
候选还没落盘，判据却已经在了。

### 这条不变量由第 12 项门禁 `content_check` 守着

```bash
mas selftest --only content_check
```

门禁要求：

* 内容机检**读得到**压缩 PDF 里的字，而**字节级机检读不到**（这一条证明测试有意义）；
* 内容机检**读得到** Word 文档里的字，而且读到的是**文字不是标记**；
* 格式检查**说得出**格式，**判得出**错；
* **读不出内容的文件判不通过**，不是「未判定」；
* **要写的新文件按将要写进去的内容判**。

而且门禁**每轮故意把内容路径打断一次**，然后确认自己**注意到了** ——
**不会失败的门禁不算门禁**。

### 为什么要加第 12 项门禁（这是反证查出来的）

第 9 项看**引擎**，第 10 项看**报告**，第 11 项看**人这条路**，
**没有任何门禁看交付物本身的内容**。

所以我们做了**反证**：拿内容路径的九个行为分别破掉，再看有没有门禁会报败：

| 变异 | 现在被捕获吗 |
| --- | --- |
| PDF 流不解压 | 是 |
| Office 文档掉进 zip 分支 | 是 |
| XML 标记不剥 | 是 |
| 内容检查去读字节而不是内容 | 是 |
| 读不出内容判成「未判定」 | 是 |
| 格式检查恒过 | 是 |
| overlay 被忽略 | 是 |
| 门禁自己不再看内容 | 是 |
| 门禁丢了一条观察 | 是 |

第一次做这个实验时，**九个变异里有三个没被捕获** ——
其中两个是**门禁自己的缝**（它可以在自己不看内容的时候照样报「全过」）。
现在的门禁把「记录观察」和「下判断」**分开**，观察少一条就会报出来。

## 循环也要能写出二进制交付物（v0.7.70）

上一节让机检**读得进** PDF。可是**读得进**只解决了一半：
**得先有一个 PDF 存在**。

而写文件协议（v0.7.15）只能带**文字**。worker 的输出是一个字符串，
引擎把它写成 UTF-8。于是**交付物是 PDF 的任务**，
worker 无论多努力都**产不出** PDF —— 验收标准判不了，循环闭不上，
而原因跟答案本身毫无关系。

### 写块现在能带 `encoding`

```
<<<MAS:FILE path="out/report.pdf" encoding="base64">>>
JVBERi0xLjQK...
<<<MAS:END FILE>>>
```

引擎把块里的内容**解码成真正的二进制**再落盘。
**不写 `encoding` 的块仍旧按文本写** —— 旧协议一点没变。

### 这条不变量由第 13 项门禁 `binary_write` 守着

```bash
mas selftest --only binary_write
```

门禁要求：

* base64 写块**落盘是真字节**，不是它的 base64 文本；
* **写出去的字节就是机检读到的字节** —— 写路径和读路径必须一致；
* **不认识的编码被拒**，**坏掉的 base64 被拒**，而且**不留半截文件**；
* 不写编码的块**仍旧按文本写**；
* **内容级标准形成写文件义务** —— 不然 worker 只会「 口头说」那个文件；
* 引擎规划的是**二进制字节**，不是旁边的文字。

而且门禁**每轮故意把写路径打断一次**，然后确认自己**注意到了**；
路径**崩了**也算「注意到了」 —— 一个只会崩的门禁比一个会报的门禁更没用。

### 为什么要加第 13 项门禁（这也是反证查出来的）

第 12 项门禁看**读**，**没有任何门禁看「写」**。

所以我们做了**反证**：拿写路径的七个行为分别破掉，再看有没有门禁会报败：

| 变异 | 现在被捕获吗 |
| --- | --- |
| overlay 装的是字节的**个数**不是字节 | 是 |
| 编码被忽略 | 是 |
| base64 被解成文本 | 是 |
| 不认识的编码被接受 | 是 |
| 内容机检不算写义务 | 是 |
| 坏 base64 被悄悄吞掉 | 是 |
| 计划里装的是编码文本 | 是 |

第一次做这个实验时，**有一个变异没被捕获** ——
而且它抓到的**不是假想的 bug，是真的**：

**overlay 装的是字节的个数，不是字节。**
并行选优要给每个候选打分，overlay 取的是 `planned["bytes"]`，
那是**长度**。于是每一份文件机检读到的都是**一个数字**而不是那个文件 ——
**会写出正确 PDF 的候选，输给了会什么都不写的候选**。

真实字节在 `planned["data"]` 里。现在 overlay 由
`LoopEngine._planned_overlay()` **统一构造**，只装 bytes，
装不进 bytes 的一律跳过。

### 一并修掉的两个小 bug

* **base64 静默吞掉垃圾** —— 宽松解码会把不在字母表里的字符全丢掉，
  于是一段纯胡话被解成**一个空文件**、一声不吭。现在**严格解码**。
* **不认识的编码被默默丢掉** —— `encoding="rot13"` 的块被拒绝了，
  但**错误信息没往外传**：没有文件、没有报错、账本里也没有线索。
  现在理由会一起交出去。

## 一个反直觉的点

**给模型更多轮次不一定提高成功率。** 如果产物在连续几轮里一模一样，那多给 10 轮只是多烧 10 轮的钱。
所以停滞检测不是「优化项」，而是**省钱项**：它把「模型卡在同一个错误上」变成一个人类立刻能看到的信号。

这也是为什么本项目把 `stagnation_limit` 默认设为 3 而不是更大。

## 怎么度量你的循环

跑完之后看账本：

```bash
mas ledger --tail 50
```

关注三个数：

- **闭合轮数**：从第一次执行到通过用了几轮（轮数越少，标准写得越清楚）；
- **判定来源分布**：`source` 里 `rule` 占比越高，结论越可复现；
- **是否升级过**：`escalated` 说明标准或目标还需要人介入，这是信息不是失败。
