# Loop Engineering：多智能体循环怎么才算闭合

## 一句话

**闭合 = 有一个可被机器判定的结束条件，并且这个判定被记录下来。**

没有这一条，多智能体系统就是一台「烧 token 的永动机」。

## 四个常见的不闭合症状

| 症状 | 表现 | 本项目的对应机制 |
| --- | --- | --- |
| 无验收标准 | 「我觉得差不多了」 | `criteria` 必填，且支持机检规则 |
| 无退出条件 | 一轮轮往下聊 | 闭合/升级/预算三种终态，二选一必须发生 |
| 无过程记录 | 出事无法复盘 | append-only 账本，每轮一条 |
| 无止损 | 走不通的任务反复重试 | 迭代/墙钟/token 三重预算 + 停滞检测 |

## 关键区分：谁的判定

一个循环能不能闭合，取决于**判定权在谁手里**。

- 判定权在模型手里 → 模型说「好了」就是好了，无法复现，无法审计；
- 判定权在引擎手里 → 同一份产物 + 同一份标准，永远得到同一个结论。

因此本项目把验收标准拆成两层：

```
验收标准
├─ 带 check  →  引擎判定（contains / min_chars / regex / json_keys ...）→ 可复现
└─ 无 check  →  模型判定（verifier 给出 pass/note）→ 不可复现，但仍然要给出证据
```

两层都通过才算闭合；模型层没给结论的，按不通过处理。

## 「机检标准」的写法

一条好标准的特征是：**读者和机器都能独立判定它成立与否。**

| 反例（不可核验） | 正例（可核验） |
| --- | --- |
| 质量要好 | 正文 ≥ 800 字且包含 3 个小节标题 |
| 不要有错别字 | 不包含 `TODO`、`待补充`、`xxx` |
| 结构清晰 | 存在 `## 背景`、`## 方案`、`## 验收` 三个标题 |
| 数据要准确 | JSON 中的 `version` 字段等于 `v0.1.0` |

写不出机检规则，往往说明**目标本身还没想清楚**。这时正确动作不是硬编一条规则，而是把目标拆细，或者接受「这条标准交给模型判定，但要求它给出证据」。

## 闭环的四个不变量

1. **闭合必须可判定**：`status` 只有 `closed` / `escalated` / `budget_exhausted` / `error`。
2. **闭合必须留痕**：闭合的那一轮一定有 `closure` 账本条目，含产物哈希与逐条判定。
3. **不判定不放行**：没有判定 = 不通过。
4. **停不下来就升级**：停滞与预算触顶都要升级人工，而不是继续空转。

## 一个反直觉的点

**给模型更多轮次不一定提高成功率。** 如果产物在连续几轮里一模一样，那多给 10 轮只是多烧 10 轮的钱。
所以停滞检测不是「优化项」，而是**省钱项**：它把「模型卡在同一个错误上」变成一个人类立刻能看到的信号。

这也是为什么本项目把 `stagnation_limit` 默认设为 3 而不是更大。

## 怎么度量你的循环

跑完之后看账本：

```bash
mas ledger --tail 50
```

关注三个数：

- **闭合轮数**：从第一次执行到通过用了几轮（轮数越少，标准写得越清楚）；
- **判定来源分布**：`source` 里 `rule` 占比越高，结论越可复现；
- **是否升级过**：`escalated` 说明标准或目标还需要人介入，这是信息不是失败。
