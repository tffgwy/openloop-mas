# 架构

## 组件

```
                       ┌──────────────┐
   goal + criteria ───▶│  LoopEngine  │───▶ RunResult(status, scores, artifact)
                       └──────┬───────┘
                              │
        ┌─────────────────────┼─────────────────────┐
        ▼                     ▼                     ▼
   ┌─────────┐          ┌──────────┐          ┌──────────┐
   │ Provider│          │  Ledger  │          │ Tickets  │
   │ mock /  │          │ JSONL    │          │ 人工升级  │
   │ oai /   │          │ append   │          │ 工单     │
   │ anthropic│         │ only     │          └──────────┘
   └─────────┘          └──────────┘
```

- **Provider**：只负责「给定提示词，返回文本」。判定权不在模型手里。
- **Ledger**：append-only 的 JSONL，每轮一条 `closure` 条目，外加 `planner` 条目。
- **Tickets**：循环无法自行闭合时的升级对象，携带完整上下文。工单只有在 `resume` **真的闭合**时才置为 `resolved`；没闭合就留在 `waiting_human` 队列里，并把失败现场追加到 `resume_attempts`，不另开重复工单。
- **Roles**：五个角色的系统提示词与任务状态模板。

## 一次循环的状态机

```
        ┌──────────┐
        │ planner  │  仅第一轮，产出 plan
        └────┬─────┘
             ▼
        ┌──────────┐
   ┌───▶│  worker  │  产出交付物 artifact
   │    └────┬─────┘
   │         ▼
   │    ┌──────────┐
   │    │ verifier │  机检 + 模型判定 -> scores
   │    └────┬─────┘
   │         ▼
   │    ┌──────────┐
   │    │ reflect  │  仅失败时，产出 issues
   │    └────┬─────┘
   │         ▼
   │    ┌──────────┐
   │    │   lead   │  close / revise / escalate
   │    └────┬─────┘
   │         │
   │    close ─────────────▶ 闭合（closed）
   │         │
   │         └─ revise ────┐
   │                      └──▶ 下一轮
   │
   └── escalate ──────────▶ 人工工单（escalated）
```

## 判定优先级

1. **机检规则优先**：只要验收标准带 `check`，结果由 `evaluate_check()` 决定，模型说什么都不影响。
2. **模型判定兜底**：没有机检规则的标准才看 `verifier` 的 `scores`。
3. **未判定不通过**：模型没给出的判定记为 `unjudged`（`source: model-missing`），判不通过。
4. **判定值按含义读取**：判定值可能是布尔，也可能是模型随手写的字符串。`bool("false")` 是 `True`，所以用真值测试读判定，会把「字符串形式的否决」变成「一票通过」——两位评审都说「不通过」也能聚合成 `pass: true`。现在统一走 `_as_bool()`：只有真布尔 `true`、数字非零、`"true"` / `"yes"` / `"1"` 算通过；`"false"` / `"no"` / `"0"` 算不通过；**读不懂的值（`"maybe"`、`null`、空串）一律不算通过票**，并在聚合结果里给出 `unreadable_votes` 计数。读不懂的判定绝不参与闭合。
5. **总结服从逐条判定**：模型回答的顶层 `verdict` 只在**没有任何一条**标准的判定读得懂时才被保留；只要有一条读得懂，顶层总结就由这些判定重新算出（全部通过才算通过）。闭合判定始终只看逐条 `scores`，但报告、回放与账本必须显示**同一个**结论——一个说「通过」而逐条说「不通过」的载荷会让读者无法判断引擎信了哪一半。
6. **机检三态**：机检结果不是两态。`pass: None` 表示**不可判定**（没有规则、规则缺参数、规则类型不认识），它既不是通过也不是失败——报告与评审提示里都显示为 `UNDECIDED`，评审模型读到的是「这条根本没被判定」，而不是「机检失败了」。不可判定的标准不会自己变成通过票。
7. **可选标准不阻塞**：`required: false` 的标准只记录。它有机检就照常跑机检、真实结果原样写进报告，只是判定闭合时跳过它（`blocking: false`）；它没有机检就由模型判定，判定结果同样只作记录。标志值按**含义**读取：`"false"` / `"0"` / `"no"` 才是可选，读不懂的值（缺失、`null`、`"maybe"`）一律按必选处理——读不懂的标志绝不能悄悄放宽标准。

这一层顺序是整个项目最重要的设计决定：**模型的乐观不能覆盖确定性证据。**

## 四道终止路径

| 终止 | 触发条件 | 结果 |
| --- | --- | --- |
| 闭合 | 全部必需标准通过 | `closed` |
| 升级 | 停滞次数 ≥ `stagnation_limit`，或 token 触顶 | `escalated` + 工单 |
| 预算 | 迭代 / 墙钟触顶 | `budget_exhausted` |
| 错误 | Provider 抛错 | `error`（账本里留痕） |

## 停滞判定

对**产物文本**取 SHA-256。连续多轮哈希相同 → 判定卡死（模型在原地打转）。
注意这比「答案看起来一样」更严格：文本有任何变化哈希就变，因此它抓的是**真正的原地打转**，而不是「同一个意思换了说法」。

## 状态目录

```
~/.mas/
├─ config.json
├─ ledgers/runs.jsonl
└─ tickets/T-YYYYMMDD-HHMMSS-xxxx.json
```

全部可用环境变量 `MAS_STATE_DIR` 覆盖，测试因此不会污染真实状态。
